## 1. 종목 수집 방식

- **상황**: 원래는 `finance.naver.com/sise/lastsearch2.naver` 의 HTML 표를 파싱했다. 이 주소가 `stock.naver.com` 으로 302 리다이렉트되고 새 페이지는 스크립트로 그려 HTML 에 표가 없다. 수집이 0건이 되면 코드는 예시 종목(삼성전자 75,000원 등)을 저장했고, 9거래일(종목-일 45건)이 그렇게 서비스됐다(로그 1·2장).
- **대안**: (a) HTML 크롤링 유지 (b) 공식 API (c) 네이버 모바일 증권 JSON 응답.
- **선택과 이유**: (c). 같은 데이터를 JSON 으로 주므로 파싱이 단순하고 서버에서 실제로 10종목이 수집됐다(로그 7장).
- **공식 API 검토 기록**: 로그 8장에 "공식 전환 후보(공공데이터포털 주식시세정보 등)는 조사만 했다"는 한 줄이 있다. 어떤 항목을 조사했고 왜 지금 쓰지 않았는지는 **기록 없음**. 이 문서에서 공식 API 를 비교했다고 말할 수 없다.
- **근거**: 실측(원인 확인: 직접 요청해 리다이렉트와 `<table>` 0개 확인, 로그 2장). 선택 자체는 "무엇을 바꾸면 되살아나는가"에 따른 것이고 대안 간 수치 비교는 없다.
- **약점과 대비책**: 이 주소는 네이버가 문서로 공개한 Open API 가 아니다(`StockCrawlerService` 주석, 로그 3-1). 구조가 바뀌면 빈 목록을 돌려주고, 호출 측이 수집 실패로 기록한다. 실패 시 DB 를 건드리지 않아 직전 데이터가 남고, 가짜 종목은 저장하지 않는다. 실패는 `pipeline_run.outcome=COLLECT_FAILED`, `/api/health` 의 `lastAttemptOk=false`, 화면 안내로 드러난다.
- **다음에 검토할 것**: 공식 API 전환 가능 여부(항목·제공 범위·갱신 주기). 현재 확인 못 함.

> 발표자가 직접 채울 것: 공식 API 를 검토했다면 어떤 것을 봤고 무엇이 부족했는지(현재 문서에 근거 없음)

## 2. 뉴스 수집과 중복 제거

- **상황**: 종목마다 관련 뉴스가 필요하다. 코드는 네이버 검색 Open API(`openapi.naver.com/v1/search/news.json`)를 쓴다(`application-prod.yml`).
- **대안**: 뉴스 페이지 크롤링. 이 대안을 실제로 시도·비교한 기록은 없다.
- **선택과 이유**: 공식 API. 구조 변경 위험이 낮다는 **판단(미측정)**. 이 프로젝트에서 크롤링 방식이 실패한 경험은 1번(종목)에서 있었다.
- **같이 한 일(실측)**: 네이버 API 호출에서 TLS 인증서 검증을 꺼두었던 코드를 제거했고 JDK 기본 신뢰 저장소로 정상 연결됨을 확인(로그 3-2). 호출 실패를 "뉴스 없음"과 구분하기 위해 종목마다 `newsStatus` 를 저장한다.
- **중복 제거**: 제목 정규화(머리말·꼬리말·문장부호·종목명 제거) → 숫자 구성이 같고 문자 2-gram 자카드 유사도 0.7 이상이면 같은 기사, 같은 링크도 중복(`NewsService`).
  - 실측: 저장된 뉴스 1,484건 중 20건(1.3%)이 중복, 종목-일 306건 중 19건(6.2%) 영향(로그 1장).
  - 숫자 일치 조건은 "1분기 영업이익 증가"와 "2분기 영업이익 증가"가 약 0.78 로 묶이는 것을 실행으로 확인하고 넣었다(로그 3-2).
  - **0.7 이라는 값을 여러 값으로 시험해 정했다는 기록은 없다.** 코드 주석과 로그 어디에도 조정 실험이 없다. 판단(미측정)이다.
- **모델에 넣는 범위: 제목 + 요약문 vs 기사 본문**
  - 사실(실측, 2026-11-18 21:03 운영 수집분 47건): 네이버 검색 API 가 주는 요약문은 109~139자(중앙값 126자)이고 47건 모두 "..." 로 잘려 있다. 모델은 기사 본문을 읽지 않는다. 요약문이 본문이 아니라 사진 설명인 기사도 있었다(이 경우 모델이 가진 정보는 사실상 제목뿐이다).
  - 따라서 이 서비스의 "주요 이슈"는 **기사 요약이 아니라 제목과 앞부분 100여 자에 기반한 이슈 정리**다. "기사를 요약한다", "원문과 대조했다"고 말하면 틀리다.
  - 본문을 수집하지 않는 이유(판단, 미측정): 같은 47건이 32개 언론사 도메인에 흩어져 있어(실측) 본문을 받으려면 사이트마다 다른 구조를 긁어야 한다. 종목 수집이 HTML 구조 변경으로 멈췄던 것(1번)과 같은 위험이고, 언론사 본문을 수집·저장하는 것은 저작권·이용약관 검토가 필요하다. 이 검토는 하지 않았다(`확인 못 함`).
  - 보완: 문장마다 근거 기사 번호와 원문 링크를 붙여 사용자가 본문을 직접 열어 볼 수 있게 했다.
  - 표본 대조(실측, `docs/experiments/2026-11-18-input-vs-fulltext-sample.md`): 같은 수집분의 이슈 문장 22개 중 20개는 인용 기사의 제목·요약문으로 뒷받침됐고, 2개는 주체가 바뀌었거나 잘린 요약문에서 추론한 것이었다. 본문을 확인할 수 있었던 13개 중 본문과 어긋난 문장은 찾지 못했고 3개는 중요한 조건이 빠져 있었다. 9개는 본문을 열지 못해 판정하지 못했다. 읽을 수 있었던 기사 31건 중 26건은 제목+요약문만으로 핵심 사실을 알 수 있었다. 평가자는 AI 한 명이고 한 시점의 표본이며, 분석 모델은 예비 모델(`gemini-3.5-flash-lite`)이었다. 같은 날 주 모델(`claude-haiku-5-5`) 결과 28문장도 같은 방법으로 봤다: 25개 뒷받침됨, 3개 일부만, 본문을 확인한 20개 중 16개 일치·4개 맥락 누락·불일치 0. 두 모델의 비율은 비슷하고 표본이 작아 우열을 말할 수 없다.
- **종목 귀속 필터(표본 대조에서 찾은 문제의 수정, 2026-11-18)**
  - 문제(실측): 종목 "에스엠"의 기사 5건 중 3건이 다른 회사 "에스엠벡셀" 기사였다. 필터가 "제목에 종목명이 들어 있는가"만 봤기 때문이다.
  - 대안: (a) 그대로 둔다 (b) 상장사 이름 목록과 대조한다 (c) 종목명 바로 뒤에 붙은 글자(꼬리)를 본다. (b) 는 목록을 구해 유지해야 해서 이번에는 하지 않았다. (c) 를 골랐다.

## 3. AI 호출 구조: 10종목 1회 vs 종목별 호출

- **상황**: 수집 사이클마다 10종목을 분석해야 한다.
- **대안**: 종목별 10회 호출.
- **선택과 이유**: 1회 호출. README 는 "비용/속도를 최적화했다"고 쓴다(`README.md` 2번 기능). 뉴스가 있는 종목만 요청에 넣는다(`GeminiAnalysisService.analyzeAllStocks`).
- **근거**: **판단(미측정)**. 종목별 호출로 같은 입력을 돌려 비교한 실험은 없다. 로그의 실험은 모두 "10종목 1회" 구조 안에서 모델을 비교했다. 1회 호출의 실측 값은 있다: 운영 서버에서 10종목, 입력 5,850 / 출력 1,812 토큰, 30.4초(로그 3-3, `gemini-2.5-flash`).
- **알려진 단점**: 한 번의 호출이 실패하면 10종목이 함께 실패한다(`AI_CALL_FAILED`). 이를 완화하려고 체인(7번)과 종목별 `INVALID_RESPONSE` 처리를 둔다. 이 단점을 설계 당시 비교했다는 기록은 없다.
- **다음에 검토할 것**: 종목별 호출 또는 2~3종목 묶음과 비용·시간·실패율 비교. 실험 도구(`modelExperiment`)로 같은 방식으로 잴 수 있다.

> 발표자가 직접 채울 것: 1회 호출을 처음 선택한 시점의 이유

## 4. 출력 형식 강제: 구조화 출력 vs 프롬프트로만 요청

- **상황**: 원래는 자유 텍스트를 `[종목N]` 태그로 잘라 썼다. 아카이브에서 응답에서 한 종목만 빠진 날이 2일 확인됐다(로그 2장).
- **대안**: (a) 기존 태그 파싱 (b) 프롬프트로 JSON 을 요청하고 파싱 (c) 제공자의 구조화 출력(JSON 스키마).
- **선택과 이유**: (c) 를 쓰고 코드에서 다시 검증한다(범위 밖 근거 번호 제거, 근거 없는 이슈 제거, 빠진 종목은 `INVALID_RESPONSE`).
- **근거**:
  - 실측: 태그 파싱의 누락 2일(36거래일 중, 로그 1장).
  - 실측: 실험 도구에는 형식 강제 사다리(SCHEMA_STRICT → SCHEMA → JSON_MODE → PROMPT_ONLY)가 있고, 400 거부 때 한 단계씩 내려간다. 3차 실행에서 성공한 모든 호출이 스키마 수준에서 받아들여졌고 한 단계 내려간 경우는 없었다(로그 4장, `run3-models.md` "형식 강제 시도 이력"). Gemini·Claude 는 SCHEMA, GPT 는 SCHEMA_STRICT.
- **비교하지 않은 것**: JSON_MODE·PROMPT_ONLY 로 실제 호출해 스키마 강제와 품질을 비교한 결과는 **없다**. 사다리는 "내려가야 할 때를 대비한 장치"이며 비교 결과가 아니다. "구조화 출력이 프롬프트 방식보다 낫다고 측정했다"고 말하면 안 된다.
- **다음에 검토할 것**: 스키마 미지원 모델(예: Gemma 는 문서에서 지원 여부 확인 못 함, `run3-models.md`)을 쓸 때 PROMPT_ONLY 품질 측정.

## 5. 근거 표시와 검증

- **상황**: 개선 전에는 어느 기사에서 나온 말인지 알 수 없었고, "AI 분석" 315건 중 217건(68.9%)이 미리 써둔 문구였다(로그 1장).
- **대안**: 검증 없이 모델 출력을 그대로 표시(원래 방식).
- **선택과 이유**: 이슈 문장마다 근거 기사 번호 `[n]` 를 요구하고, 코드가 범위 밖 번호와 근거 없는 이슈를 제거한다. 관점·리스크는 "AI 해석"으로 구분 표기한다. 뉴스가 없는 종목은 분석을 요청하지 않는다(`NO_NEWS`). 프롬프트에는 뉴스에 없는 수치 금지, 뉴스 안의 지시문 무시, 매수·매도 권유·목표주가 금지 지침이 있다(로그 3-3).
- **근거**:
  - 실측: 4개 모델의 3차 실행에서 근거 유효율은 모두 100%(예: Claude 84/84). 이 지표로는 모델 차이가 드러나지 않았다(로그 4장).
  - 실측: 수치 근거 일치율(문장 속 숫자가 인용 기사에 문자열로 있는가). 프롬프트 B 에서 네 모델의 문장 속 숫자 360개 전부 확인(로그 4-2).
  - 운영에서는 수치를 **측정만 하고 문장은 고치지 않는다**(`pipeline_run.numbers_total / numbers_unverified`, `GeminiAnalysisService`).
- **한계**: 수치 일치는 환각의 증명이 아니라 문자열 점검이다. "2조"와 "20,000억"은 불일치로, 맥락이 달라도 같은 숫자면 일치로 잡힌다(로그 4장 한계). 근거 번호가 실제 기사를 가리키는 것과 문장이 기사 내용에 충실한 것은 다르다. 후자는 표본 한 번(문장 22개)으로만 확인했다(2번 절의 표본 대조). 운영에서 상시 측정하지는 않는다.

- **상황**: 폴백 목록이 `gemini-2.5-flash → gemini-2.0-flash → gemini-1.5-flash` 였다(커밋 `21f7be2d`). `gemini-2.0-flash` 는 2026-06-01 종료된 모델이라 폴백을 추가한 시점(07-30)에 이미 쓸 수 없었다(로그 2장, 요약 도구로 읽은 종료 일정). 결과: 36거래일 중 25일 전 종목이 고정 문구, 전 종목 실제 분석은 9일(로그 1장).

## 8. DB

- **상황**: 운영은 외부 PostgreSQL(Neon), 서버에는 DB 가 없다. 로컬·테스트는 H2(`build.gradle`, `application-prod.yml`, `DEPLOY.md` 5장).
- **선택 유지의 이유**: 처음 이 조합을 고른 이유는 이 세션에서 확인되지 않았다. 이번 개선에서 바꾸지 않았다.
- **개선과 관련된 판단**: 스키마는 `ddl-auto: update` 로 자동 생성한다. 새 상태값은 `PipelineRun.trigger/outcome` 과 `Stock.analysisFailReason` 을 일반 문자열 컬럼으로 두었다. 이유는 코드 주석에 있다: 운영 PostgreSQL 에서 `update` 는 enum CHECK 제약을 갱신하지 못해 값을 추가할 때 문제가 되기 때문이다(`PipelineRun.java`, `AnalysisFailReason.java` 주석). 이 현상을 직접 재현한 기록은 없다. 판단(주석 근거).
- **주의(문서 정정)**: `Stock.analysisStatus`(`AnalysisStatus`)와 `Stock.newsStatus`(`NewsStatus`)는 `@Enumerated(EnumType.STRING)` 으로 **enum 컬럼**이다. "새 상태값을 전부 문자열로 추가했다"고 말하면 틀린다. 문자열로 둔 것은 이번에 추가한 값들이다.
- **한계**: Neon 플랜의 백업·시점 복구 제공 여부는 `확인 못 함`(`DEPLOY.md` 7-1 `[확인 필요]`). `pg_dump` 절차와 복원 시험 점검표는 문서에 있으나 이번 개선에서 복원을 실제로 시험했다는 기록은 없다. `ddl-auto: update` 는 컬럼 삭제·변경을 하지 못하므로 스키마 변경 이력 관리 도구(Flyway 등) 도입은 검토 과제다.

## 13. 빌드 위치: 서버 vs CI 러너

- **상황**: 서버 설치 직후 실측: 메모리 total 961Mi, available 405Mi, 디스크 9.8G 중 여유 1.9G(`DEPLOY.md` 4-2, 로그 6장).
- **대안**: 서버에서 `docker compose up --build` 로 Gradle 빌드.
- **선택**: GitHub Actions 러너에서 `./gradlew bootJar` 후 JAR 을 `scp` 로 전송, 서버는 JRE 이미지에 JAR 만 넣어 실행(`Dockerfile.runtime`, `deploy-backend.yml`).
- **근거**: 실측(서버 가용 자원). 문서의 논리는 "JDK 이미지·Gradle 배포판·의존성 캐시가 필요한데 여유 디스크 1.9GB 와 가용 메모리 405MB 로는 감당하기 어렵다"이다. **서버에서 실제로 빌드를 시도해 실패했다는 기록은 없다.** 가용 자원과 필요 자원의 비교에 근거한 판단이다.
- **부작용(실측)**: 첫 배포 직후 디스크 93%(여유 748M). 빌드 캐시 정리 후 79%. 워크플로가 배포마다 `docker builder prune -af` 를 실행한다(로그 6·7장).
- **한계**: 서버가 JAR 로 이미지를 만든다. 이미지를 CI 에서 빌드해 레지스트리에서 pull 하면 서버의 빌드 단계가 없어지고 태그로 되돌리기도 쉽다는 것이 `DEPLOY.md` 의 다음 개선이다.

## 14. 컨테이너·JVM 설정

- **설정**: `mem_limit: 512m`, `-XX:MaxRAMPercentage=50`(힙 약 256MB), `-XX:+UseSerialGC`, `-XX:+ExitOnOutOfMemoryError`, 로그 순환 10MB × 3, 비 root 사용자 실행, 컨테이너 `restart: unless-stopped`(`docker-compose.server.yml`, `Dockerfile.runtime`).
- **근거**:
  - 512MB 와 50%: 서버 실측 가용 메모리 405MB 를 근거로 한 출발값(`Dockerfile.runtime` 주석). 첫 배포 직후 실측: 컨테이너 266.6MiB / 512MiB(52%), CPU 0.36%(대기 상태), 서버 used 653Mi, available 308Mi, 스왑 227Mi 사용(`DEPLOY.md` 4-3). 스왑 2GB 와 `vm.swappiness=10` 설정.
  - SerialGC: 주석의 이유는 "1 vCPU 소형 서버에서 GC 스레드·메모리 오버헤드 최소화"다. 다른 GC 와 비교해 잰 기록은 없다. **판단(미측정)**.
  - OOM 시 종료 후 재기동: 정책 선택이며 시험 기록은 없다.
- **한계**: 측정한 값은 "첫 배포 직후 대기 상태"뿐이다. 분석 사이클이 도는 동안의 최대 메모리, 스왑 사용 추이, OOM 발생 여부(`OOMKilled`)는 이 문서 작성 시점에 확인 못 함. 새 의존성(Anthropic SDK)이 추가된 JAR 의 메모리 사용량도 배포 후 다시 재야 한다.

## 15. 프론트 배포와 API 프록시

- **상황**: 프론트는 Vercel, 백엔드는 HTTP `:8080` 이다. `frontend/vercel.json` 이 `/api/*` 를 `http://211.188.54.232:8080/api/*` 로 rewrite 한다.
- **대안**: 브라우저가 백엔드를 직접 호출.
- **선택과 이유**: 커밋 메시지 `1a24ff4f` 는 "avoid mixed-content, no backend HTTPS needed" 라고 적었다. HTTPS 인 Vercel 페이지가 HTTP 백엔드를 직접 부르면 브라우저가 막는 혼합 콘텐츠 문제를 피하려는 것이다. 이 이유는 커밋 메시지로 확인했을 뿐 문서로 대조하지는 않았다. **판단(미측정)**. Vercel 과 CRA 자체는 기존 선택 유지.
- **한계**: Vercel → 백엔드 구간은 평문 HTTP 다(로그 8장). 8080 은 Vercel 출발 IP 가 고정이 아니라 소스를 좁히지 못해 `0.0.0.0/0` 으로 열려 있다(`DEPLOY.md` 2장). 서버 IP 가 바뀌면 `vercel.json` 을 고쳐야 하고 빠뜨리면 화면만 죽는다. 도메인과 리버스 프록시(Caddy 등)로 TLS 를 종단하는 것이 다음 개선이다.

> 발표자가 직접 채울 것: 처음에 React·Tailwind·Vercel 을 고른 이유

## 16. CI/CD

- **구성**: `ci.yml` 은 모든 푸시·PR 에서 백엔드 테스트(JDK 17)와 프론트 빌드(Node 20, `CI=true`)를 돌린다. `deploy-backend.yml` 은 `main` 푸시(백엔드·compose·워크플로 변경 시) 또는 수동 실행에서만 돌고, `ci.yml` 을 재사용해 통과해야 JAR 빌드·SSH 전송·기동으로 간다. 기동 후 `/api/health` 를 최대 36회 × 5초 재시도하고 실패하면 로그와 되돌리는 방법을 출력한다. 배포는 동시에 한 건만(`concurrency`), 직전 JAR 은 `app.jar.prev` 로 남는다.
- **대안**: 서버에서 직접 빌드·수동 배포(개선 전, 테스트 없음, 로그 0장).
- **근거**: 실측: 개선 전 백엔드 테스트 0개 → 로그 작성 시점 125개(로그 0장) → 2026-11-18 모델 체인 변경 커밋(`80ec9924`) 기준 158개 → 종목 귀속 필터 추가 후 168개(실패 0, 오류 0, 건너뜀 3, `./gradlew test` 실행 결과). 배포 키 문제(`error in libcrypto`)를 풀고 자동 배포가 성공했다고 로그 7장이 기록한다.
- **문서 간 불일치**: `DEPLOY.md` 4-5 마지막 줄은 "이 파이프라인은 실제 서버에서 아직 실행해 본 적이 없다"고 적혀 있으나 로그 6·7장에는 첫 배포 측정값과 자동 배포 성공이 있다. 앞의 문장이 옛 것이다. 발표에서는 로그 쪽을 쓴다.
- **한계**: 호스트 키는 실행마다 `ssh-keyscan` 으로 받은 것을 신뢰한다(최초 신뢰). 경로상 중간자 공격을 막지 못한다. 22번 포트를 `0.0.0.0/0` 으로 연 것은 자동 배포를 유지하기 위한 선택이며 키 전용 로그인·fail2ban 으로 보완했다(`DEPLOY.md` 2장 선택 A). 프론트는 Vercel 이 별도로 배포한다. 백엔드 배포 워크플로의 `paths` 에 프론트가 없다. 프론트 변경이 CI 빌드에서 걸러지는 것은 `ci.yml` 이다. 롤백은 이전 커밋 재배포 또는 `app.jar.prev` 복구이며 실제로 롤백을 실행해 본 기록은 없다.

## 면접에서 나올 만한 질문과 답의 근거

1. **왜 공식 API 가 아니라 비공식 JSON 을 썼나?**
   - 답의 근거: 이 문서 1번, 로그 2·3-1·8장. 원래 HTML 이 개편으로 사라져 수집이 멈췄고 같은 데이터를 주는 JSON 으로 교체했다. 공식 API 를 비교한 기록은 없다. 비공식이라는 점과, 바뀌면 실패를 상태값으로 드러내고 가짜 데이터를 만들지 않는 대비책을 함께 말한다. "공식 API 전환 후보를 조사만 했다"가 로그의 전부다.

2. **AI 가 거짓 내용을 만들면 어떻게 아나?**
   - 답의 근거: 이 문서 5번, 로그 3-3·4장. 문장마다 근거 기사 번호를 요구하고 코드가 검증하며, 숫자는 인용 기사 문자열과 대조해 측정한다(프롬프트 B 에서 360개 전부 확인). 문장이 기사 내용에 충실한지는 표본 한 번(문장 22개)으로 확인했고 그 결과와 한계는 `docs/experiments/2026-11-18-input-vs-fulltext-sample.md` 에 있다. 모델이 기사 본문이 아니라 제목과 요약문 100여 자만 본다는 점을 먼저 말한다.

3. **왜 이 모델을 골랐나?**
   - 답의 근거: 이 문서 6번, 로그 4·4-2장, `docs/experiments/`. 4개 모델을 같은 입력으로 3회씩 3차례 실측했다. 결과 수치를 말하고 "3회, 한 시점이라 확정이 아니다"를 붙인다. "GPT 가 더 싼데 왜 Haiku 인가"라는 후속 질문에는 6번의 비교(숫자 포함 비율은 비슷, 비용 차이는 월 1달러 미만, 응답 시간은 Haiku 가 절반)를 그대로 말한다.

4. **한 회사 모델만 쓰면 안 되나? 왜 두 회사인가?**
   - 답의 근거: 이 문서 7번, 로그 1·2장. 폴백이 이미 종료된 모델이라 36일 중 25일이 고정 문구였다. 이것은 "폴백을 검증해야 한다"의 근거다. "두 회사여야 한다"는 판단이고, 첫 모델이 왜 자주 실패했는지는 미확인이라고 정직하게 말한다.

5. **10종목을 한 번에 호출하면 한 번 실패할 때 전부 실패하지 않나?**
   - 답의 근거: 이 문서 3번. 맞다. 종목별 호출과 비교해 본 적이 없다. 완화책은 체인과 종목별 `INVALID_RESPONSE` 이고, 비교 실험은 다음 과제다.

6. **서버를 1GB 로 운영하는데 안정적인가?**
   - 답의 근거: 이 문서 13·14번, `DEPLOY.md` 4-2·4-3, 로그 6장. 첫 배포 직후 컨테이너 266.6MiB / 512MiB, 스왑 227Mi 사용, 디스크 93% → 79% 를 말한다. 부하 중 최대 사용량과 장기 안정성은 측정하지 않았다고 말한다.

7. **보안은 어떻게 챙겼나?**
   - 답의 근거: 이 문서 11·12·16번, 로그 3장·6장, `DEPLOY.md` 1~3장. 관리 API 무인증(200) → 토큰(401), TLS 검증 해제 제거, 키가 로그에 남던 것 수정, SSH 키 전용·root 차단·방화벽 이중·fail2ban·자동 보안 업데이트. 남은 것: Vercel → 백엔드 평문 HTTP, 22번 포트 전체 공개, 호스트 키 최초 신뢰. 노출됐던 DB 비밀번호·API 키 교체 필요(로그 8장).

8. **서버가 죽거나 DB 를 잃으면 어떻게 복구하나?**
   - 답의 근거: `DEPLOY.md` 7장, 이 문서 8·12번. 서버는 문서 절차로 다시 세울 수 있고 EC2 → 새 서버 이전이 실제 사례다. DB 는 `pg_dump` 절차가 있으나 복원을 실제로 시험한 기록과 Neon 의 자체 백업 보존 기간은 현재 근거 없음 — 이렇게 답하는 것이 정직하다.

9. **왜 Prometheus 같은 모니터링 도구를 쓰지 않았나?**
   - 답의 근거: 이 문서 10번. 서버 메모리 제약 때문에 DB 이력과 헬스 API 로 대신했다는 판단이다. 모니터링 스택을 올려 비용을 재 보지는 않았다. 알림이 없다는 한계를 먼저 말한다.

10. **이 프로젝트에서 본인이 한 일과 AI 도구가 한 일은?**
    - 답의 근거: 로그 10장 마지막 항목. Claude Code 를 써서 만들었다는 사실을 밝히고, 본인의 몫(문제 정의, 판단, 서버 구성, 키 관리, 검증 확인)과 도구의 몫을 구분해 말한다. 구체적 구분은 발표자가 직접 채운다.

11. **공공기관 환경이라면 무엇을 바꾸겠나?**
    - 현재 근거 없음 — 이렇게 답하는 것이 정직하다. 이 프로젝트에서 공공기관 요건(예: 인증 범위)을 검토한 기록이 없다. 확인된 사실은 네이버클라우드 공식 사이트에 CSAP 인증서 항목이 있다는 것까지이고, 사용 중인 서버 유형이 그 범위에 드는지는 확인 못 함. 말할 수 있는 것은 이 문서의 한계 항목(HTTPS 종단, 접근 통제 강화, 백업 복원 시험, 알림, 스키마 이력 관리)을 우선순위로 제시하는 것까지다.
