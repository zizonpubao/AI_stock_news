## 1. 종목 수집 방식

- **상황**: 원래는 `finance.naver.com/sise/lastsearch2.naver` 의 HTML 표를 파싱했다. 이 주소가 `stock.naver.com` 으로 302 리다이렉트되고 새 페이지는 스크립트로 그려 HTML 에 표가 없다. 수집이 0건이 되면 코드는 예시 종목(삼성전자 75,000원 등)을 저장했고, 9거래일(종목-일 45건)이 그렇게 서비스됐다(로그 1·2장).
- **대안**: (a) HTML 크롤링 유지 (b) 공식 API (c) 네이버 모바일 증권 JSON 응답.
- **선택과 이유**: (c). 같은 데이터를 JSON 으로 주므로 파싱이 단순하고 서버에서 실제로 10종목이 수집됐다(로그 7장).
- **공식 API 검토 기록**: 로그 8장에 "공식 전환 후보(공공데이터포털 주식시세정보 등)는 조사만 했다"는 한 줄이 있다. 어떤 항목을 조사했고 왜 지금 쓰지 않았는지는 **기록 없음**. 이 문서에서 공식 API 를 비교했다고 말할 수 없다.
- **근거**: 실측(원인 확인: 직접 요청해 리다이렉트와 `<table>` 0개 확인, 로그 2장). 선택 자체는 "무엇을 바꾸면 되살아나는가"에 따른 것이고 대안 간 수치 비교는 없다.
- **약점과 대비책**: 이 주소는 네이버가 문서로 공개한 Open API 가 아니다(`StockCrawlerService` 주석, 로그 3-1). 구조가 바뀌면 빈 목록을 돌려주고, 호출 측이 수집 실패로 기록한다. 실패 시 DB 를 건드리지 않아 직전 데이터가 남고, 가짜 종목은 저장하지 않는다. 실패는 `pipeline_run.outcome=COLLECT_FAILED`, `/api/health` 의 `lastAttemptOk=false`, 화면 안내로 드러난다.
- **다음에 검토할 것**: 공식 API 전환 가능 여부(항목·제공 범위·갱신 주기). 현재 확인 못 함.

- **공식 API 로 바꾸지 않은 이유(판단)**: 이 서비스가 필요한 것은 시세가 아니라 "지금 사람들이 많이 찾는 종목 순위"다. 이 순위는 네이버 증권 서비스가 만드는 데이터다. 공공데이터포털의 주식시세정보 같은 공식 API 는 시세를 주는 것으로 조사했고(로그 8장), 검색 순위를 대신할 수 없다고 판단했다. 그래서 비공식 주소를 쓰되 실패를 감지하고 드러내는 쪽(위 약점과 대비책)을 택했다. 공식 API 의 제공 항목을 하나씩 대조한 기록은 없다.

## 2. 뉴스 수집과 중복 제거

- **상황**: 종목마다 관련 뉴스가 필요하다. 코드는 네이버 검색 Open API(`openapi.naver.com/v1/search/news.json`)를 쓴다(`application-prod.yml`).
- **대안**: 뉴스 페이지 크롤링. 이 대안을 실제로 시도·비교한 기록은 없다.
- **검색 방식과 사후 측정(2026-11-19)**: 검색어는 종목명을 큰따옴표로 감싼 문자열(`"종목명"`), 관련도순, 30건이다. 이 방식을 고를 때 다른 검색 방식과 비교하지는 않았다. 사후에 표본 150건(현재 수집분 47건 전부 + 아카이브 무작위 103건)을 AI 분류자 둘이 서로 결과를 보지 않고 분류했다(일치 96.7%). 둘 다 투자 관련으로 본 기사가 134건(89.3%), 종목과 무관하거나 다른 회사인 기사는 2건이었다. 약점은 두 가지다. 종목명 표기가 기사 제목과 다른 종목은 5건을 못 채운다(현재 `JYP Ent.` 2건, 아카이브 `삼성전자우` 평균 2.75건). 내용이 시세뿐인 자동 기사가 들어온다(현재 8.5%, 아카이브 15.9%). 다른 검색 방식과의 비교는 **미측정**이다. 상세는 `docs/experiments/2026-11-19-news-query-relevance.md`.

    | 분석 성공 | 10 / 10 | 10 / 10 |

    - 본문 글자 수는 629~1,497자(중앙값 1,113자), 합계 48,336자다(`GET /api/stocks/{id}/news` 의 `bodyChars`).
    - 원문 주소(`originallink`) 확인: 링크가 네이버 뉴스 주소인 기사 10건 중 6건이 본문 사용, 4건이 추출 실패였고 robots 제외는 0건이었다. 서버 로그로 확인(같은 실행의 `본문 수집` 로그 47줄): 요청한 호스트에 `n.news.naver.com` 은 없었다. 네이버 링크였던 기사는 `mk.co.kr`, `mt.co.kr`, `khan.co.kr`, `imaeil.com` 등 언론사 원문 주소로 요청됐다. 추출 실패 4건의 호스트는 `busan.com` 2건, `donga.com` 1건, `fnnews.com` 1건이다. 이 세 곳은 지정한 본문 표시에 걸리지 않았거나 본문이 200자 미만이었고(둘 중 어느 쪽인지는 미확인), 요약문으로 분석됐다. 개별 규칙은 추가하지 않았다.

    - 본문을 넣은 뒤의 문장 품질은 아직 대조하지 않았다. **"본문을 넣어 환각이 줄었다"고 말할 수 없다.**
    - 언론사별 이용약관은 확인하지 않았다. 여러 기사 본문 끝에 "무단전재 및 재배포 금지"가 적혀 있다. 이 서비스는 본문을 저장·표시·재배포하지 않지만, 분석 입력으로 쓰는 것이 허용 범위인지 법적 검토는 하지 않았다.
    - 언론사가 페이지 구조를 바꾸면 추출이 실패한다. 그 경우 요약문으로 돌아가고 실행 이력의 실패 건수로 드러난다.
    - 백엔드 테스트: 216개(실패 0, 오류 0, 건너뜀 3). 네트워크를 쓰지 않고 지어낸 HTML·robots 문자열로만 검증한다.
- **종목 귀속 필터(표본 대조에서 찾은 문제의 수정, 2026-11-18)**
  - 문제(실측): 종목 "에스엠"의 기사 5건 중 3건이 다른 회사 "에스엠벡셀" 기사였다. 필터가 "제목에 종목명이 들어 있는가"만 봤기 때문이다.

## 3. AI 호출 구조: 10종목 1회 vs 종목별 호출

- **상황**: 수집 사이클마다 10종목을 분석해야 한다.
- **대안**: 종목별 10회 호출.
- **선택과 이유**: 1회 호출. README 는 "비용/속도를 최적화했다"고 쓴다(`README.md` 2번 기능). 뉴스가 있는 종목만 요청에 넣는다(`GeminiAnalysisService.analyzeAllStocks`).
- **근거**: **판단(미측정)**. 종목별 호출로 같은 입력을 돌려 비교한 실험은 없다. 로그의 실험은 모두 "10종목 1회" 구조 안에서 모델을 비교했다. 1회 호출의 실측 값은 있다: 운영 서버에서 10종목, 입력 5,850 / 출력 1,812 토큰, 30.4초(로그 3-3, `gemini-2.5-flash`).
- **알려진 단점**: 한 번의 호출이 실패하면 10종목이 함께 실패한다(`AI_CALL_FAILED`). 이를 완화하려고 체인(7번)과 종목별 `INVALID_RESPONSE` 처리를 둔다. 이 단점을 설계 당시 비교했다는 기록은 없다.
- **다음에 검토할 것**: 종목별 호출 또는 2~3종목 묶음과 비용·시간·실패율 비교. 실험 도구(`modelExperiment`)로 같은 방식으로 잴 수 있다.

- **1회 호출로 둔 이유(판단, 미측정)**: (1) 호출 수가 하루 13회다. 종목별로 부르면 130회가 되어 호출 한도와 실패 지점이 10배가 된다. (2) 지시문(규칙, 출력 형식)이 요청마다 한 번만 들어간다. 종목별 호출은 같은 지시문을 10번 보낸다. (3) 구조화 출력의 `stockIndex` 로 종목별 결과를 나눠 받을 수 있어 한 번에 보내도 결과를 섞지 않는다(4번). 단점(한 번 실패하면 10종목이 함께 실패)은 모델 체인(7번)으로 줄였다. 종목별 호출과 비용·시간을 실측으로 비교하지는 않았다.

## 4. 출력 형식 강제: 구조화 출력 vs 프롬프트로만 요청

- **상황**: 원래는 자유 텍스트를 `[종목N]` 태그로 잘라 썼다. 아카이브에서 응답에서 한 종목만 빠진 날이 2일 확인됐다(로그 2장).
- **대안**: (a) 기존 태그 파싱 (b) 프롬프트로 JSON 을 요청하고 파싱 (c) 제공자의 구조화 출력(JSON 스키마).
- **선택과 이유**: (c) 를 쓰고 코드에서 다시 검증한다(범위 밖 근거 번호 제거, 근거 없는 이슈 제거, 빠진 종목은 `INVALID_RESPONSE`).
- **근거**:
  - 실측: 태그 파싱의 누락 2일(36거래일 중, 로그 1장).
  - 실측: 실험 도구에는 형식 강제 사다리(SCHEMA_STRICT → SCHEMA → JSON_MODE → PROMPT_ONLY)가 있고, 400 거부 때 한 단계씩 내려간다. 3차 실행에서 성공한 모든 호출이 스키마 수준에서 받아들여졌고 한 단계 내려간 경우는 없었다(로그 4장, `run3-models.md` "형식 강제 시도 이력"). Gemini·Claude 는 SCHEMA, GPT 는 SCHEMA_STRICT.
- **비교하지 않은 것**: JSON_MODE·PROMPT_ONLY 로 실제 호출해 스키마 강제와 품질을 비교한 결과는 **없다**. 사다리는 "내려가야 할 때를 대비한 장치"이며 비교 결과가 아니다. "구조화 출력이 프롬프트 방식보다 낫다고 측정했다"고 말하면 안 된다.
- **다음에 검토할 것**: 스키마 미지원 모델(예: Gemma 는 문서에서 지원 여부 확인 못 함, `run3-models.md`)을 쓸 때 PROMPT_ONLY 품질 측정.

## 5. 근거 표시와 검증

- **상황**: 개선 전에는 어느 기사에서 나온 말인지 알 수 없었고, "AI 분석" 315건 중 217건(68.9%)이 미리 써둔 문구였다(로그 1장).
- **대안**: 검증 없이 모델 출력을 그대로 표시(원래 방식).
- **선택과 이유**: 이슈 문장마다 근거 기사 번호 `[n]` 를 요구하고, 코드가 범위 밖 번호와 근거 없는 이슈를 제거한다. 관점·리스크는 "AI 해석"으로 구분 표기한다. 뉴스가 없는 종목은 분석을 요청하지 않는다(`NO_NEWS`). 프롬프트에는 뉴스에 없는 수치 금지, 뉴스 안의 지시문 무시, 매수·매도 권유·목표주가 금지 지침이 있다(로그 3-3).
- **근거**:
  - 실측: 4개 모델의 3차 실행에서 근거 유효율은 모두 100%(예: Claude 84/84). 이 지표로는 모델 차이가 드러나지 않았다(로그 4장).
  - 실측: 수치 근거 일치율(문장 속 숫자가 인용 기사에 문자열로 있는가). 프롬프트 B 에서 네 모델의 문장 속 숫자 360개 전부 확인(로그 4-2).
  - 운영에서는 수치를 **측정만 하고 문장은 고치지 않는다**(`pipeline_run.numbers_total / numbers_unverified`, `GeminiAnalysisService`).
- **한계**: 수치 일치는 환각의 증명이 아니라 문자열 점검이다. "2조"와 "20,000억"은 불일치로, 맥락이 달라도 같은 숫자면 일치로 잡힌다(로그 4장 한계). 근거 번호가 실제 기사를 가리키는 것과 문장이 기사 내용에 충실한 것은 다르다. 후자는 표본 한 번(문장 22개)으로만 확인했다(2번 절의 표본 대조). 운영에서 상시 측정하지는 않는다.

## 8. DB

- **상황**: 운영은 외부 PostgreSQL(Neon), 서버에는 DB 가 없다. 로컬·테스트는 H2(`build.gradle`, `application-prod.yml`, `DEPLOY.md` 5장).
- **선택 유지의 이유**: 처음 이 조합을 고른 이유는 이 세션에서 확인되지 않았다. 이번 개선에서 바꾸지 않았다.
- **개선과 관련된 판단**: 스키마는 `ddl-auto: update` 로 자동 생성한다. 새 상태값은 `PipelineRun.trigger/outcome` 과 `Stock.analysisFailReason` 을 일반 문자열 컬럼으로 두었다. 이유는 코드 주석에 있다: 운영 PostgreSQL 에서 `update` 는 enum CHECK 제약을 갱신하지 못해 값을 추가할 때 문제가 되기 때문이다(`PipelineRun.java`, `AnalysisFailReason.java` 주석). 이 현상을 직접 재현한 기록은 없다. 판단(주석 근거).
- **주의(문서 정정)**: `Stock.analysisStatus`(`AnalysisStatus`)와 `Stock.newsStatus`(`NewsStatus`)는 `@Enumerated(EnumType.STRING)` 으로 **enum 컬럼**이다. "새 상태값을 전부 문자열로 추가했다"고 말하면 틀린다. 문자열로 둔 것은 이번에 추가한 값들이다.
- **한계**: Neon 플랜의 백업·시점 복구 제공 여부는 `확인 못 함`(`DEPLOY.md` 7-1 `[확인 필요]`). `pg_dump` 절차와 복원 시험 점검표는 문서에 있으나 이번 개선에서 복원을 실제로 시험했다는 기록은 없다. `ddl-auto: update` 는 컬럼 삭제·변경을 하지 못하므로 스키마 변경 이력 관리 도구(Flyway 등) 도입은 검토 과제다.

- **선택 사유**:
  1. **DB 를 서버 밖에 둔다.** 서버 메모리가 1GB 이고 애플리케이션 컨테이너가 대기 상태에서 약 310MiB 를 쓴다(실측, 14번). 같은 서버에 DB 를 올리면 메모리를 나눠 써야 한다. 관리형 DB(Neon)를 쓰면 서버는 애플리케이션만 돌리고, 서버를 새로 만들어도 데이터가 남는다(서버를 옮긴 뒤에도 2026-07~09 의 아카이브가 그대로 조회됐다).
  2. **PostgreSQL 은 표준 SQL 을 따르는 오픈소스 DB 다.** JPA 로 접근하므로 특정 회사 DB 에 묶인 SQL 이 거의 없고, 나중에 기관 내부 DB 로 옮기는 부담이 작다(판단).
  3. **로컬·테스트는 H2 를 쓴다.** 테스트가 외부 DB 없이 돌아 CI 에서 매 푸시마다 216개를 실행할 수 있다(실측).
- **대안과의 비교(일반 특성, 이 프로젝트에서 측정하지 않음)**:

  | 후보 | 이 서비스의 요구에 비춰 본 점 |
  |---|---|
  | 관리형 PostgreSQL, Neon (현재) | 서버 메모리를 쓰지 않는다. 서버와 DB 사이가 인터넷 구간이라 연결 설정(TLS)이 필요하다. 플랜의 백업 범위는 확인 못 함. |
  | 같은 서버에 PostgreSQL·MySQL 설치 | 외부 의존이 없고 지연이 작다. 1GB 서버의 메모리를 나눠 써야 하고 백업·패치를 직접 해야 한다. |
  | 다른 관리형 DB (Supabase 등) | 구성은 비슷하다. 비교해 보지 않았다. |

- **질문을 받으면**: 후보를 실측으로 비교해 고른 것은 아니다. "서버 제약(메모리 1GB)에 맞춰 DB 를 밖에 두는 구성을 택했고, 그 제약은 실측으로 확인했다"가 사실과 맞는 답이다.

## 9. 스케줄링

- **상황**: 평일 8~20시 매시 정각에 수집 → 뉴스 → AI 분석, 16:05 일일 아카이브(`StockScheduler`, `application.yml`).
- **확인 필요(2026-11-19)**: 설정은 8~20시이지만 2026-11-19 실행 기록(`GET /api/runs`, 10:20 조회)에는 08:00 실행이 없고 09:00(id 9)과 10:00(id 10)만 있다. 정기 실행은 먼저 오늘이 거래일인지 확인하고, 아니라고 판단하면 실행 기록 없이 건너뛴다(`StockScheduler.scheduledUpdate`, `MarketPriceService.isTradingToday`). 08:00 정각에 이 확인이 "거래일 아님"으로 나온 것으로 **추정**하며 서버 로그로 확인하지 않았다. 확인 전에는 "8시부터 실행된다"고 단정하지 않는다.
- **대안**: 외부 cron, 별도 워커·큐. 비교 기록 없음.
- **선택**: 애플리케이션 내부 `@Scheduled`(기존 선택 유지). 서버를 1대, 메모리 1GB 로 운영하는 상황에서 별도 프로세스를 두지 않는다는 점이 유리하다는 것은 판단이다.
- **이번에 추가한 것**:
  - 중복 실행 방지: `AtomicBoolean` 으로 스케줄·시작·수동 갱신이 겹치면 건너뛴다. 겹치면 종목 테이블을 서로 지우고 AI 호출이 중복되기 때문이다(`StockScheduler` 주석).
  - 실행 이력: 매 사이클 `pipeline_run` 1행(트리거, 단계별 결과, 모델, 토큰, 소요, 결론).
  - 휴장일 감지(`isTradingToday`)와 오늘 수집분이 없으면 아카이브 건너뛰기.
- **근거**: 기존 선택 유지. 실행 이력 실측 값은 5장에 2회분뿐이다(2/2 수집 성공, 20/20건 분석 성공).
- **한계**: `AtomicBoolean` 은 프로세스 안에서만 유효하다. 서버를 2대로 늘리면 중복 방지가 되지 않는다(분산 락 필요). 앱이 꺼져 있으면 스케줄도 실행되지 않는다. 오래된 이력 정리 로직 없음(로그 8장).

## 10. 운영 관측

- **상황**: 개선 전에는 36일 중 25일의 실패를 몰랐다(로그 0·1장).
- **대안**: Prometheus/Grafana 등 별도 모니터링 스택. 검토·시험 기록 없음.
- **선택**: DB 에 쌓는 `pipeline_run` + 공개 읽기 전용 `GET /api/health`, `/api/runs`, `/api/runs/summary`. 화면 상단에 최근 24시간 성공 횟수 등을 표시한다.
- **이유**: 서버 메모리가 1GB 이고 가용 메모리가 405MB 였다는 실측(로그 6장)이 있어, 추가 프로세스를 두기 부담스러웠다. 그러나 모니터링 스택을 올려서 실제로 얼마나 드는지 재 본 기록은 없다. **판단(미측정)**.
- **한계**: 이력은 알림을 보내지 않는다. 사람이 조회해야 한다(`DEPLOY.md` 다음 개선: 실패 알림). 로그 보관은 Docker `json-file` 10MB × 3개 순환(`docker-compose.server.yml`).

## 11. 관리 API 보호

- **상황**: `POST /api/archive/run` 이 인증 없이 200 을 돌려주며 예시 종목 5개를 그날 아카이브로 저장했다. 수정본은 401(로그 3-5, 실행 비교).
- **대안**: Spring Security 전체 도입.
- **선택**: `AdminTokenInterceptor` 가 `X-Admin-Token` 헤더를 `ADMIN_TOKEN` 환경변수와 상수 시간 비교한다. 대상 경로는 `/api/stocks/refresh`, `/api/archive/run`, `/api/admin/**`. `ADMIN_TOKEN` 이 비어 있으면 403 으로 닫는다(열려 있는 것보다 닫혀 있는 편이 안전). 실패는 401. CORS 사전 요청은 통과.
- **이유**: 보호할 경로가 3개이고 사용자 계정 개념이 없다. **판단(미측정)**. Spring Security 를 도입했을 때의 비용(메모리, 설정 복잡도)은 재 보지 않았다.
- **같이 고친 보안 약점(실측, 로그 3장)**: TLS 검증 해제 제거, Gemini 키를 URL 쿼리에서 헤더로 이동(원본은 실패 로그에 키가 3회 남았고 수정본은 0회).
- **한계**: 공유 토큰 하나, 호출자 구분·감사 로그·속도 제한 없음. 조회용 API 는 전부 공개(`GET`). HTTPS 가 아닌 구간에서는 토큰이 평문으로 지나간다(15번 참조).

## 12. 호스팅

- **상황**: 데모 백엔드가 502 였다. EC2 를 쓸 수 없는 상태였다(로그 7장 "EC2 사용 불가"). 이전 EC2 에서는 재부팅 때 IP 가 바뀌어 Vercel 프록시 주소를 두 번 고쳤다(`DEPLOY.md` 1-1, 커밋 `8f160407`, `197699d5`).
- **선택**: 네이버클라우드 VPC 서버 `mi1-g3`(vCPU 1, 메모리 1GB, 디스크 10GB, Ubuntu 24.04, KVM)(로그 6장, 콘솔에서 확인한 사양). 공인 IP 이용료는 콘솔 안내 기준 월 4,032원(`DEPLOY.md` 1-1). Micro 서버는 공식 문서상 한국 리전 전용·계정당 1대·체험용이고 기본 스토리지 10GB 까지 무료라고 `DEPLOY.md` 에 적혀 있다(그 문장에 URL 은 없다).
- **선정 경위(작업 대화 기록, 문서에는 없음)**: 이전 후보로 처음 나온 것은 해외 PaaS(Fly.io, Render)였다. 발표자가 "공공기관에서 많이 쓰는 곳" 기준을 제시해 국내 클라우드로 방향을 바꿨고 네이버클라우드로 정했다. 후보 간 가격·성능을 실측으로 비교하지는 않았다. **판단(미측정)**.
- **검토했다가 접은 대안**: 위 경위 말고 다른 클라우드와 비교한 내용은 문서에 **없다**. 문서에 나오는 대안은 22번 포트 접근 방식(A~D)과 DB 의 Supabase 정도다. 첫 배포 설정은 Railway 용 Dockerfile 이었다(커밋 `aa25c732`). Railway 에서 EC2 로 옮긴 이유는 기록 없음.
- **서버 월 비용**: 문서에 적힌 실측값 없음(`확인 못 함`). 공인 IP 월 4,032원만 있다.
- **공공기관 관점의 사실 확인(문서 확인)**: 네이버클라우드 공식 페이지(https://www.ncloud.com/intro/securityNotice/materials, 확인일 2026-11-18)의 정보보호 인증서 목록에 "CSAP 인증서"가 있고 설명은 "네이버 클라우드 플랫폼 CSAP 인증서입니다."가 전부다. 인증 등급, 서비스 범위, 유효기간은 그 페이지 본문에 없었다. KISA CSAP 인증 현황 페이지는 열지 못했다(`확인 못 함`). 따라서 "이 프로젝트가 쓰는 Micro 서버가 CSAP 인증 범위에 든다"는 말은 **하지 않는다**. 발표에서는 "공식 사이트에 CSAP 인증서 항목이 있다"까지만 말할 수 있다.
- **보안 설정(실측)**: 배포 전용 계정, SSH 키 로그인만, root 원격 접속 차단 후 `Permission denied (publickey)` 확인, ACG 와 ufw 두 겹 방화벽(22, 8080), fail2ban, unattended-upgrades(로그 6장, `DEPLOY.md` 1~3장). 단 Docker 가 공개한 포트는 ufw 를 우회하므로 8080 의 실질 방어선은 ACG 라고 문서가 밝혔다.
- **한계**: 단일 서버, 체험용 사양(성능 보장 없음). 서버를 잃었을 때의 복구 절차는 문서에 있고(`DEPLOY.md` 7-4) 이번 EC2 → 새 서버 이전이 실제 사례이지만, 복구 시간은 측정하지 않았다.

- **발표용 정리**: 발표 자료에는 "백엔드는 네이버클라우드 VPC 서버에서 Docker 로 운영한다"고 쓰면 된다(현재 사실). 선택 사유는 세 가지다. (1) 공공기관이 쓰는 국내 클라우드 사업자다(공식 페이지에 CSAP 인증서 게시, 위 "공공기관 관점의 사실 확인"). (2) 한국 리전이라 국내 사용자와 네이버 API 호출 구간이 국내에 있다(판단, 지연 미측정). (3) 가장 작은 서버로 시작해 자원 제약 안에서 운영하는 경험을 쌓을 수 있다(메모리·디스크 실측, 13·14번). 이전 서버 이야기는 발표에 넣지 않아도 된다. 운영 환경 이력을 직접 물으면 위 "상황" 그대로 답한다.

## 13. 빌드 위치: 서버 vs CI 러너

- **상황**: 서버 설치 직후 실측: 메모리 total 961Mi, available 405Mi, 디스크 9.8G 중 여유 1.9G(`DEPLOY.md` 4-2, 로그 6장).
- **대안**: 서버에서 `docker compose up --build` 로 Gradle 빌드.
- **선택**: GitHub Actions 러너에서 `./gradlew bootJar` 후 JAR 을 `scp` 로 전송, 서버는 JRE 이미지에 JAR 만 넣어 실행(`Dockerfile.runtime`, `deploy-backend.yml`).
- **근거**: 실측(서버 가용 자원). 문서의 논리는 "JDK 이미지·Gradle 배포판·의존성 캐시가 필요한데 여유 디스크 1.9GB 와 가용 메모리 405MB 로는 감당하기 어렵다"이다. **서버에서 실제로 빌드를 시도해 실패했다는 기록은 없다.** 가용 자원과 필요 자원의 비교에 근거한 판단이다.
- **부작용(실측)**: 첫 배포 직후 디스크 93%(여유 748M). 빌드 캐시 정리 후 79%. 워크플로가 배포마다 `docker builder prune -af` 를 실행한다(로그 6·7장).
- **한계**: 서버가 JAR 로 이미지를 만든다. 이미지를 CI 에서 빌드해 레지스트리에서 pull 하면 서버의 빌드 단계가 없어지고 태그로 되돌리기도 쉽다는 것이 `DEPLOY.md` 의 다음 개선이다.

## 14. 컨테이너·JVM 설정

- **설정**: `mem_limit: 512m`, `-XX:MaxRAMPercentage=50`(힙 약 256MB), `-XX:+UseSerialGC`, `-XX:+ExitOnOutOfMemoryError`, 로그 순환 10MB × 3, 비 root 사용자 실행, 컨테이너 `restart: unless-stopped`(`docker-compose.server.yml`, `Dockerfile.runtime`).
- **근거**:
  - 512MB 와 50%: 서버 실측 가용 메모리 405MB 를 근거로 한 출발값(`Dockerfile.runtime` 주석). 첫 배포 직후 실측: 컨테이너 266.6MiB / 512MiB(52%), CPU 0.36%(대기 상태), 서버 used 653Mi, available 308Mi, 스왑 227Mi 사용(`DEPLOY.md` 4-3). Anthropic SDK 가 들어간 JAR 로 바꾼 뒤 실측(2026-11-19 새벽, id 6 실행을 마친 대기 상태, 본문 수집 배포 전): 컨테이너 304.2MiB / 512MiB(59.41%), CPU 0.10%. 스왑 2GB 와 `vm.swappiness=10` 설정.
  - SerialGC: 주석의 이유는 "1 vCPU 소형 서버에서 GC 스레드·메모리 오버헤드 최소화"다. 다른 GC 와 비교해 잰 기록은 없다. **판단(미측정)**.
  - OOM 시 종료 후 재기동: 정책 선택이며 시험 기록은 없다.
- **한계**: 측정한 값은 세 번의 대기 상태뿐이다(266.6MiB, 304.2MiB, 본문 수집 배포 후 310.9MiB). 분석 사이클이 도는 동안의 최대 메모리, 스왑 사용 추이, OOM 발생 여부(`OOMKilled`)는 확인 못 함. 실행 도중의 값은 재지 않았다.

## 15. 프론트 배포와 API 프록시

- **상황**: 프론트는 Vercel, 백엔드는 HTTP `:8080` 이다. `frontend/vercel.json` 이 `/api/*` 를 `http://211.188.54.232:8080/api/*` 로 rewrite 한다.
- **대안**: 브라우저가 백엔드를 직접 호출.
- **선택과 이유**: 커밋 메시지 `1a24ff4f` 는 "avoid mixed-content, no backend HTTPS needed" 라고 적었다. HTTPS 인 Vercel 페이지가 HTTP 백엔드를 직접 부르면 브라우저가 막는 혼합 콘텐츠 문제를 피하려는 것이다. 이 이유는 커밋 메시지로 확인했을 뿐 문서로 대조하지는 않았다. **판단(미측정)**. Vercel 과 CRA 자체는 기존 선택 유지.
- **한계**: Vercel → 백엔드 구간은 평문 HTTP 다(로그 8장). 8080 은 Vercel 출발 IP 가 고정이 아니라 소스를 좁히지 못해 `0.0.0.0/0` 으로 열려 있다(`DEPLOY.md` 2장). 서버 IP 가 바뀌면 `vercel.json` 을 고쳐야 하고 빠뜨리면 화면만 죽는다. 도메인과 리버스 프록시(Caddy 등)로 TLS 를 종단하는 것이 다음 개선이다.

- **React 를 고른 이유**: 18번 절에 있다(발표자 확인, 2026-11-19). Tailwind 와 Vercel 을 고른 이유는 따로 확인된 것이 없다(기존 선택 유지).

## 16. CI/CD

- **구성**: `ci.yml` 은 모든 푸시·PR 에서 백엔드 테스트(JDK 17)와 프론트 빌드(Node 20, `CI=true`)를 돌린다. `deploy-backend.yml` 은 `main` 푸시(백엔드·compose·워크플로 변경 시) 또는 수동 실행에서만 돌고, `ci.yml` 을 재사용해 통과해야 JAR 빌드·SSH 전송·기동으로 간다. 기동 후 `/api/health` 를 최대 36회 × 5초 재시도하고 실패하면 로그와 되돌리는 방법을 출력한다. 배포는 동시에 한 건만(`concurrency`), 직전 JAR 은 `app.jar.prev` 로 남는다.
- **대안**: 서버에서 직접 빌드·수동 배포(개선 전, 테스트 없음, 로그 0장).
- **근거**: 실측: 개선 전 백엔드 테스트 0개 → 로그 작성 시점 125개(로그 0장) → 2026-11-18 모델 체인 변경 커밋(`80ec9924`) 기준 158개 → 종목 귀속 필터 추가 후 168개(실패 0, 오류 0, 건너뜀 3, `./gradlew test` 실행 결과). 배포 키 문제(`error in libcrypto`)를 풀고 자동 배포가 성공했다고 로그 7장이 기록한다.
- **문서 간 불일치**: `DEPLOY.md` 4-5 마지막 줄은 "이 파이프라인은 실제 서버에서 아직 실행해 본 적이 없다"고 적혀 있으나 로그 6·7장에는 첫 배포 측정값과 자동 배포 성공이 있다. 앞의 문장이 옛 것이다. 발표에서는 로그 쪽을 쓴다.
- **한계**: 호스트 키는 실행마다 `ssh-keyscan` 으로 받은 것을 신뢰한다(최초 신뢰). 경로상 중간자 공격을 막지 못한다. 22번 포트를 `0.0.0.0/0` 으로 연 것은 자동 배포를 유지하기 위한 선택이며 키 전용 로그인·fail2ban 으로 보완했다(`DEPLOY.md` 2장 선택 A). 프론트는 Vercel 이 별도로 배포한다. 백엔드 배포 워크플로의 `paths` 에 프론트가 없다. 프론트 변경이 CI 빌드에서 걸러지는 것은 `ci.yml` 이다. 롤백은 이전 커밋 재배포 또는 `app.jar.prev` 복구이며 실제로 롤백을 실행해 본 기록은 없다.

## 17. 백엔드 언어·프레임워크

- **선택**: Java 17, Spring Boot 3.5, Spring Data JPA(`build.gradle`).
- **선택 사유**:
  1. **공공 정보시스템에서 쓰는 기술 계열이다.** 전자정부 표준프레임워크 5.0 실행환경 문서는 공통기반이 "Spring Framework 6.2 Core Technologies 를 기반"으로 한다고 적는다(문서 확인, 2026-11-19, https://egovframework.github.io/egovframe-docs/egovframe-runtime/ ). 이 프로젝트의 Spring Boot 3.5 도 Spring Framework 6.2.19 를 쓴다(실측, `gradlew dependencyInsight`). 같은 계열의 기술로 만들었다.
  2. **필요한 기능이 한 프레임워크 안에 있다.** 정기 실행(`@Scheduled`), DB 접근(JPA), REST API, 테스트 도구를 추가 서버나 별도 도구 없이 쓴다(실제 사용, `build.gradle`). 서버 1대, 메모리 1GB 에서 별도 작업 서버를 두지 않아도 된다.
  3. **정적 타입과 테스트.** 수집·검증 로직을 순수 함수로 나눠 216개 테스트로 고정했다(실측). 응답 스키마, 상태값 같은 계약을 컴파일 단계에서 확인한다.
- **대안과의 비교(대안의 특성은 일반적으로 알려진 내용이고 이 프로젝트에서 측정한 것이 아니다)**:

  | 후보 | 이 서비스의 요구에 비춰 본 점 |
  |---|---|
  | Java + Spring Boot (현재) | 위 세 가지. 메모리를 많이 쓴다: 컨테이너 대기 310.9MiB / 512MiB(실측, 14번). 1GB 서버에서 빌드할 수 없어 CI 로 옮겼다(13번). |
  | Node.js (Express, NestJS) | 프론트와 같은 언어이고 메모리 사용이 더 적다고 알려져 있다(미측정). 스케줄러·ORM 을 따로 골라 붙여야 한다. |
  | Python (FastAPI, Django) | AI·데이터 처리 라이브러리가 많다. 이 서비스의 AI 사용은 API 호출 한 번이라 그 이점이 크지 않다(판단). |

- **대가**: 메모리 사용이 크다. 그 결과로 빌드를 CI 로 옮기고(13번) 컨테이너 한도와 힙을 실측에 맞춰 정했다(14번).
- **질문을 받으면**: 후보 간 성능을 실측으로 비교해 고른 것은 아니다. "직무 분야의 표준 기술 계열이고 필요한 기능을 한 프레임워크로 해결할 수 있어 골랐으며, 메모리라는 대가는 실측하고 대응했다"가 사실과 맞는 답이다.

## 18. 프론트엔드 프레임워크

- **선택**: React 18, Tailwind CSS 3, Create React App(`react-scripts` 5.0.1), Axios(`frontend/package.json`).
- **선택 사유**: (1) 화면을 컴포넌트 단위로 나누는 구조라 유지보수가 쉽다. (2) 종목 카드를 고르면 같은 화면에서 상세 패널이 바뀌는 한 화면 서비스라 SPA 가 맞다. (3) 익숙한 기술이라 화면보다 수집·분석 쪽 개선에 시간을 쓸 수 있었다.
- **이 프로젝트에서 확인되는 사실(실측)**: 화면이 컴포넌트 4개로 나뉘어 있다(`Header`, `StockCard`, `NewsPanel`, `RunStatusLine`). 이번 개선에서 실행 상태 표시(`RunStatusLine`)를 새 컴포넌트로 추가했고, 근거 번호와 뉴스 논조 표시는 `NewsPanel` 안에서 고쳤다.
- **대안과의 비교(대안의 특성은 일반적으로 알려진 내용이고 이 프로젝트에서 측정한 것이 아니다)**:

  | 후보 | 이 서비스의 요구에 비춰 본 점 |
  |---|---|
  | React SPA (현재) | 카드 선택, 날짜 전환, 근거 번호 클릭이 페이지 이동 없이 한 화면에서 일어난다. 프론트(HTTPS, Vercel)와 백엔드(HTTP)가 분리돼 혼합 콘텐츠 문제가 생겼고 프록시로 풀었다(15번). |
  | 서버 렌더링 (Thymeleaf, JSP) | 백엔드와 한 서버에서 나가므로 프록시와 별도 프론트 배포가 필요 없다. 화면을 바꿀 때마다 서버를 다녀와야 하고, 1GB 서버가 화면 렌더링까지 맡는다. |
  | Vue | 컴포넌트 구조는 비슷하다. 비교하지 않았다. |

- **한계**: 후보를 실측으로 비교하지는 않았다. Tailwind 는 별도 CSS 파일 없이 컴포넌트 안에서 스타일을 관리하려고 쓴다(판단). Create React App 은 React 팀이 더 이상 권장하지 않는다고 알려진 도구다(이 문서를 쓰면서 공식 글로 다시 대조하지 않았다). Vite 등으로 옮기는 것이 남은 과제다.

## 면접에서 나올 만한 질문과 답의 근거

1. **왜 공식 API 가 아니라 비공식 JSON 을 썼나?**
   - 답의 근거: 이 문서 1번, 로그 2·3-1·8장. 원래 HTML 이 개편으로 사라져 수집이 멈췄고 같은 데이터를 주는 JSON 으로 교체했다. 공식 API 를 비교한 기록은 없다. 비공식이라는 점과, 바뀌면 실패를 상태값으로 드러내고 가짜 데이터를 만들지 않는 대비책을 함께 말한다. "공식 API 전환 후보를 조사만 했다"가 로그의 전부다.

2. **AI 가 거짓 내용을 만들면 어떻게 아나?**
   - 답의 근거: 이 문서 5번, 로그 3-3·4장. 문장마다 근거 기사 번호를 요구하고 코드가 검증하며, 숫자는 인용 기사 문자열과 대조해 측정한다(프롬프트 B 에서 360개 전부 확인). 문장이 기사 내용에 충실한지는 표본 한 번(문장 22개)으로 확인했고 그 결과와 한계는 `docs/experiments/2026-11-18-input-vs-fulltext-sample.md` 에 있다. 그 표본은 요약문 입력 시절의 것이다. 11-19 부터 수집이 허용된 기사는 본문 앞부분(최대 1,500자)을 입력으로 쓰고(운영 한 번 측정에서 47건 중 43건), 나머지는 제목과 요약문 100여 자만 본다는 점을 먼저 말한다. 본문 입력 뒤의 문장을 본문과 대조한 적은 없다.

3. **왜 이 모델을 골랐나?**
   - 답의 근거: 이 문서 6번, 로그 4·4-2장, `docs/experiments/`. 4개 모델을 같은 입력으로 3회씩 3차례 실측했다. 결과 수치를 말하고 "3회, 한 시점이라 확정이 아니다"를 붙인다. "GPT 가 더 싼데 왜 Haiku 인가"라는 후속 질문에는 6번의 비교(숫자 포함 비율은 비슷, 비용 차이는 월 1달러 미만, 응답 시간은 Haiku 가 절반)를 그대로 말한다.

4. **한 회사 모델만 쓰면 안 되나? 왜 두 회사인가?**
   - 답의 근거: 이 문서 7번, 로그 1·2장. 폴백이 이미 종료된 모델이라 36일 중 25일이 고정 문구였다. 이것은 "폴백을 검증해야 한다"의 근거다. "두 회사여야 한다"는 판단이고, 첫 모델이 왜 자주 실패했는지는 미확인이라고 정직하게 말한다.

5. **10종목을 한 번에 호출하면 한 번 실패할 때 전부 실패하지 않나?**
   - 답의 근거: 이 문서 3번. 맞다. 종목별 호출과 비교해 본 적이 없다. 완화책은 체인과 종목별 `INVALID_RESPONSE` 이고, 비교 실험은 다음 과제다.

6. **서버를 1GB 로 운영하는데 안정적인가?**
   - 답의 근거: 이 문서 13·14번, `DEPLOY.md` 4-2·4-3, 로그 6장. 첫 배포 직후 컨테이너 266.6MiB / 512MiB, 스왑 227Mi 사용, 디스크 93% → 79% 를 말한다. 부하 중 최대 사용량과 장기 안정성은 측정하지 않았다고 말한다.

7. **보안은 어떻게 챙겼나?**
   - 답의 근거: 이 문서 11·12·16번, 로그 3장·6장, `DEPLOY.md` 1~3장. 관리 API 무인증(200) → 토큰(401), TLS 검증 해제 제거, 키가 로그에 남던 것 수정, SSH 키 전용·root 차단·방화벽 이중·fail2ban·자동 보안 업데이트. 남은 것: Vercel → 백엔드 평문 HTTP, 22번 포트 전체 공개, 호스트 키 최초 신뢰. 노출됐던 DB 비밀번호·API 키 교체 필요(로그 8장).

8. **서버가 죽거나 DB 를 잃으면 어떻게 복구하나?**
   - 답의 근거: `DEPLOY.md` 7장, 이 문서 8·12번. 서버는 문서 절차로 다시 세울 수 있고 EC2 → 새 서버 이전이 실제 사례다. DB 는 `pg_dump` 절차가 있으나 복원을 실제로 시험한 기록과 Neon 의 자체 백업 보존 기간은 현재 근거 없음 — 이렇게 답하는 것이 정직하다.

9. **왜 Prometheus 같은 모니터링 도구를 쓰지 않았나?**
   - 답의 근거: 이 문서 10번. 서버 메모리 제약 때문에 DB 이력과 헬스 API 로 대신했다는 판단이다. 모니터링 스택을 올려 비용을 재 보지는 않았다. 알림이 없다는 한계를 먼저 말한다.

10. **이 프로젝트에서 본인이 한 일과 AI 도구가 한 일은?**
    - 답의 근거: 로그 10장 마지막 항목. Claude Code 를 써서 만들었다는 사실을 밝히고, 본인의 몫(문제 정의, 판단, 서버 구성, 키 관리, 검증 확인)과 도구의 몫을 구분해 말한다. 구체적 구분은 발표자가 직접 채운다.

11. **공공기관 환경이라면 무엇을 바꾸겠나?**
    - 현재 근거 없음 — 이렇게 답하는 것이 정직하다. 이 프로젝트에서 공공기관 요건(예: 인증 범위)을 검토한 기록이 없다. 확인된 사실은 네이버클라우드 공식 사이트에 CSAP 인증서 항목이 있다는 것까지이고, 사용 중인 서버 유형이 그 범위에 드는지는 확인 못 함. 말할 수 있는 것은 이 문서의 한계 항목(HTTPS 종단, 접근 통제 강화, 백업 복원 시험, 알림, 스키마 이력 관리)을 우선순위로 제시하는 것까지다.
