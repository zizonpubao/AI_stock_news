## 1. 실측: 기존 서비스는 실제로 어떤 상태였나

**방법.** 운영 DB 의 아카이브를 공개 조회 API(`/api/archive/...`)로 전부 내려받아 분석했다.
대상은 2026-07-29 ~ 2026-09-23 의 36거래일, 종목-일 315건이다.
"미리 써둔 문구"는 코드에 하드코딩돼 있던 문장(`📈 주요 이슈 / - 실적 개선 기대감으로 외국인 및 기관 순매수 유입 …`)과 앞부분이 일치하는지로 판정했다.

| 측정 항목 | 결과 |
|---|---|
| 미리 써둔 문구가 "AI 분석"으로 저장된 건 | 315건 중 217건 (68.9%) |
| 그날 전 종목이 미리 써둔 문구였던 날 | 36일 중 25일 |
| 전 종목이 실제 AI 분석이었던 날 | 36일 중 9일 |
| 한 종목만 미리 써둔 문구였던 날 (응답에서 그 종목만 빠짐) | 2일 |
| 예시 종목(삼성전자 75,000원 +5.63% 등 5개)이 저장된 날 | 9일 (2026-09-11 ~ 09-23), 종목-일 45건 |
| 실제 AI 분석 98건 중 뉴스가 0건이었던 것 | 3건 |
| 저장된 뉴스 1,484건 중 중복 (새 규칙으로 판정) | 20건 (1.3%), 영향받은 종목-일 306건 중 19건 (6.2%) |

**알게 된 것.**
- 가짜 데이터는 가정이 아니라 실제로 서비스되고 있었다.
- 2026-09-11 부터는 수집 대상인 네이버 금융 인기검색 페이지가 개편되어(4장 참고) 예시 종목이 9거래일 동안 저장됐다.
- 커밋 기록에는 2026-07-29 ~ 30 에 "재시도·모델 폴백으로 더미 분석 출력 문제 해결"이 있다. 그러나 그 뒤 34거래일 중 24일이 여전히 전부 미리 써둔 문구였다. **실패가 그럴듯한 문구에 가려져 있어, 고쳤는지 확인할 방법이 없었다.**
- 뉴스 중복은 예상보다 작았다(1.3%). 중복 제거는 적용했지만 핵심 문제는 아니었다. 대신 다른 종목이 주인공인 기사가 제목에 이름이 스쳤다는 이유로 들어가는 관련성 문제가 눈에 띄었다(미해결, 8장).

## 2. 원인 추적

| 현상 | 원인 | 확인 방법 |
|---|---|---|
| 수집 0건 → 예시 종목 저장 | `finance.naver.com/sise/lastsearch2.naver` 가 `stock.naver.com` 으로 302 리다이렉트되고, 새 페이지는 스크립트로 그려 HTML 에 표가 없음 | 직접 요청해 리다이렉트와 `<table>` 0개 확인 |
| AI 호출 실패가 잦음 | 폴백 목록의 `gemini-2.0-flash` 가 2026-06-01 종료된 모델. 폴백을 추가한 시점(07-30)에 이미 쓸 수 없었음 | Gemini 공식 종료 일정 문서 (요약 도구로 읽음) |
| 응답에서 한 종목만 빠짐 | 자유 텍스트를 `[종목N]` 태그로 잘라 쓰는 방식이 형식 오차에 약함 | 아카이브에서 2일 확인 |
| 실패를 몰랐음 | 실패 시 대체 문구·예시 종목을 저장하고, 실행 결과를 어디에도 남기지 않음 | 코드와 아카이브 |

첫 모델(`gemini-2.5-flash`)이 왜 그렇게 자주 실패했는지(과부하, 한도 등)는 당시 기록이 없어 **미확인**이다. 지금은 실행 이력이 남으므로 앞으로는 알 수 있다.

## 3. 적용한 개선 (데이터 흐름 순서)

### 3-1. 종목 수집
- **문제**: 원본 페이지 개편으로 수집 0건. 기존 코드는 이때 예시 종목을 저장.
- **조치**: 네이버 모바일 증권의 JSON 응답으로 수집 소스 교체. 실패하면 DB 를 건드리지 않고 직전 수집분 유지.
- **확인**: 같은 조건에서 원본과 수정본을 각각 실행해 비교(2026-11-18).

| 상황 | 원본 코드 | 수정 후 |
|---|---|---|
| 수집 소스 장애 시 화면 | 삼성전자 75,000원 +5.63% 등 예시 5종목 + 미리 써둔 "AI 분석" | 예시 없음, "최근 종목 수집에 실패했습니다" 안내 |
| 같은 시각 실제 삼성전자 | 189,800원 (-3.56%) | (수집 복구 후 실제 값 표시) |

- **한계**: 새 수집 주소는 네이버가 문서로 공개한 Open API 가 아니다. 구조가 바뀌면 빈 목록을 돌려주고 실패로 기록·표시한다.

### 3-2. 뉴스 수집
- 호출 실패를 "뉴스 없음"과 구분: 종목마다 `newsStatus`(성공/실패/대기) 저장, 화면에 "뉴스를 수집하지 못했습니다" 표시.
- 중복 기사 제거: 제목 정규화 + 숫자 일치 + 문자 2-gram 자카드 0.7 이상, 같은 링크. (숫자 일치 조건은 "1분기 영업이익 증가"와 "2분기 영업이익 증가"가 유사도 약 0.78 로 묶이는 것을 실행으로 확인하고 넣음)
- TLS 인증서 검증을 꺼두었던 코드 제거. JDK 기본 신뢰 저장소로 네이버 서버와 정상 연결됨을 확인.
- **모델에 들어가는 글(2026-11-18 까지의 운영 상태)**: 네이버 검색 API 가 주는 기사 제목과 요약문만 들어간다. 2026-11-18 21:03 운영 수집분 47건의 요약문은 109~139자(중앙값 126자)이고 47건 모두 "..." 로 잘려 있다. 서비스는 이 시점까지 기사 본문을 읽지 않았다. 요약문이 본문이 아니라 사진 설명인 기사도 1건 확인됐다(이 기사에서 모델이 가진 정보는 사실상 제목뿐). 그래서 "주요 이슈"는 기사 요약이 아니라 제목과 앞부분 100여 자에 기반한 이슈 정리다. 보완으로 문장마다 근거 기사 번호와 원문 링크를 붙였다(결정 기록 2번 절).
- **기사 본문 수집 (2026-11-19 구현, 커밋 `89cabc07`, 같은 날 00:55 운영 배포)**
  - 이유: 잘린 요약문의 빈자리를 모델이 채운 사례가 반복해 나왔다(5-3).
  - 방법: 기사 링크의 본문 앞부분(최대 1,500자, 문장 끝에서 자름)을 가져와 요약문 대신 모델에 넣는다. 요청 전에 robots.txt 를 확인하고, 전체 금지이거나 검색·인용형 AI 수집기를 이름으로 금지한 호스트는 건너뛴다. 학습용 수집기(GPTBot 등)만 금지한 호스트는 수집한다(이 서비스는 기사를 학습에 쓰지 않는다). 네이버 뉴스(`n.news.naver.com`)는 robots.txt 가 전체 금지이고 AI 학습·RAG 목적 접근을 금지한다고 적어 두어 가져오지 않는다. 본문을 못 가져온 기사는 요약문을 그대로 쓴다. 사진은 수집하지 않고, 본문은 저장·표시하지 않는다.
  - 작업 PC 에서 잰 값(운영 11-18 23:49 수집분 47건의 링크, 서버 측정 아님): 본문 사용 38건, robots 전체 금지로 제외 9건(네이버 링크), 추출 실패 0건. 본문 길이 533~1,498자(중앙값 1,128자).
  - 운영 서버에서 잰 값(2026-11-19 00:55 실행, id 7, 한 번): 본문 사용 43 / 47, robots 제외 0, 추출 실패 4(요약문 사용). 링크가 네이버 뉴스 주소인 기사 10건은 모두 언론사 원문 주소로 시도했고 6건이 본문 사용, 4건이 추출 실패였다. 입력 토큰 9,827 → 53,237, 분석 소요 40.6초 → 42.1초, 전체 소요 61.1초 → 71.6초. 1회 비용 약 $0.0056 → 약 $0.0096, 월 약 $2.6(계산값·추정). 확인 안 된 숫자 0 / 96.
  - 규칙·대안·미확인 사항은 `docs/ARCHITECTURE_DECISIONS.md` 2번 절 "본문 수집으로 변경"에 있다.
- **종목 귀속 필터 (표본 대조 중 발견, 2026-11-18 수정, 커밋 `d2f399fd`)**
  - 문제: 종목 "에스엠"의 기사 5건 중 3건이 다른 회사 "에스엠벡셀"의 기사였고, 이슈 문장도 에스엠 종목 아래에 에스엠벡셀의 배터리 공급계약을 썼다. 원인은 관련성 필터가 "제목에 종목명이 들어 있는가"만 본 것이다(`NewsService`).
  - 규칙: 제목에서 종목명 뒤에 한글·영문·숫자가 이어지면 다른 단어의 일부로 보고 제외한다. 조사(는, 의, 에서 등)와 "그룹", "사장" 같은 꼬리는 허용하고, 종목명이 독립 단어로 한 번이라도 나오면 통과한다(`NewsService.mentionsAsOwnWord`). 상장사 이름 목록과 대조하는 방법도 검토했으나 목록을 구해 유지해야 해서 하지 않았다.
  - 허용 목록의 근거(실측): 과거 아카이브 1,487건과 운영 수집분 47건의 제목에서 종목명 뒤 꼬리를 셌다. 아카이브에서 종목명이 나온 1,501곳 중 1,415곳(94%)은 꼬리가 없었다. 관찰된 조사·접미 표현 15개를 넣었고, 관찰하지 못한 조사는 문법 근거로 넣었다(판단).
  - 같은 데이터에 규칙을 적용한 결과: 운영 수집분 47건 중 4건 제외(에스엠벡셀 3건, 하이브재팬 1건). 아카이브 1,487건 중 29건(1.9%) 제외. 29건 중 13건은 따로 상장된 회사(카카오뱅크·카카오게임즈·카카오페이), 14건은 자회사·브랜드(삼성전자서비스, 카카오엔터 등), 2건은 ETF 상품명 기사다.
  - 부작용: 자회사 기사는 제목에 모회사 이름이 독립 단어로 없으면 함께 제외된다(하이브재팬 인수 기사가 그 예. 같은 사건을 다룬 다른 기사 2건은 통과했다). 종목명과 이름이 똑같은 다른 회사, 제목에는 종목명이 있지만 주인공이 다른 종목인 기사는 여전히 걸러내지 못한다.

### 3-3. AI 분석
- **뉴스가 있는 종목만 분석을 요청**한다. 없는 종목은 분석하지 않고 사유(`NO_NEWS`)를 남긴다. 근거 없이 추측한 분석을 만들지 않기 위함.
- **구조화 출력(JSON 스키마)** 으로 받고 코드에서 검증한다: 범위를 벗어난 근거 번호 제거, 근거 없는 이슈 제거, 응답에 빠진 종목은 `INVALID_RESPONSE`.
- **주요 이슈 문장마다 근거 기사 번호**를 붙인다. 관점·리스크는 "AI 해석"으로 구분 표기.
- 프롬프트 지침: 뉴스에 없는 수치·사실 금지, 뉴스 안의 지시문처럼 보이는 문장 무시, 매수·매도 권유와 목표 주가 금지.
- **실제 응답한 모델, 분석 시각, 뉴스 논조**를 종목마다 저장. 화면의 고정 문자열 "Gemini 2.5 Flash" 제거.
- 종료된 모델을 폴백 목록에서 제거.
- **두 회사 모델 체인(2026-11-18, 커밋 `80ec9924`)**: 기본 체인은 `claude:claude-haiku-5-5`(주) → `gemini:gemini-3.5-flash-lite`(예비)다(`GeminiAnalysisService.DEFAULT_CHAIN`, 환경변수 `ANALYSIS_MODELS` 로 바꿀 수 있고 비어 있으면 기본값). 앞 모델이 실패(호출 오류·거절·잘림·JSON 해석 실패)하면 다음 모델로 넘어가고, 키가 없는 제공자는 건너뛴다. **체인의 모든 모델이 실패하면 대체 문구를 만들지 않고 `AI_CALL_FAILED` 로 기록한다.** 코드 변경 기록상 이 커밋에 추가된 테스트 `AnalysisChainTest` 가 있으나, 운영 장애 상황의 검증은 아니다(결정 기록 7번).
- **수치 근거 측정을 운영 이력에 남김**: 분석이 끝나면 이슈 문장 속 숫자 중 인용 기사(제목+요약문)에서 찾지 못한 것의 수를 센다. 실행 이력에 `numbersTotal`(숫자 총수)과 `numbersUnverified`(확인 안 된 수)로 남는다. **측정만 하고 문장은 고치지 않는다.** 이 검사는 문자열 일치라서 "436,000원"과 "43만6000원"처럼 표기만 다른 경우를 불일치로 잡는다(5-1, 7장).
- Gemini API 키를 URL 쿼리에서 요청 헤더로 이동. 원본은 호출 실패 로그에 키가 3회 남았고 수정본은 0회.
- **확인(체인 전환 전)**: 운영 서버에서 실제 호출(2026-11-18 18:52) — 10종목 모두 성공, 근거 번호 부착, 모델 `gemini-2.5-flash`, 입력 5,850 / 출력 1,812 토큰, AI 분석 30.4초. 체인 전환 뒤의 실행은 5장.

### 4-2. 프롬프트 실험: 숫자 인용은 모델의 차이인가, 지시의 차이인가

**의문.** 위 결과에서 이슈 문장에 숫자가 들어간 비율이 모델마다 달랐다(같은 프롬프트에서 Claude Haiku 약 60%, Gemini 3.5 Flash-Lite 약 23%). 그런데 "숫자를 인용하라"는 지시를 프롬프트에 넣으면 다른 모델도 그렇게 할 수 있다. 모델을 고르기 전에 이 둘을 분리해서 재야 한다. 또 숫자를 쓰라고 시키면 기사에 없는 숫자를 지어낼 위험이 커지는지도 봐야 한다.

**설계.** 두 프롬프트를 비교했다(2026-11-18 19:38, 4차 실행).
- A(BASE): 운영 프롬프트 그대로.
- B(NUMBERS): 운영 프롬프트 뒤에 아래 지침을 덧붙임.
  > 주요 이슈를 쓸 때, 근거로 인용하는 기사에 수치(금액, 비율, 수량, 순위, 날짜 등)가 있으면 그 수치를 문장에 그대로 포함하세요. 기사에 없는 수치는 절대 쓰지 마세요. 수치가 없는 기사라면 수치 없이 쓰세요.
- 모델 4개 × 프롬프트 2개 × 3회 = 24회 호출. 시간대에 따른 서버 상태 차이가 섞이지 않도록 모델마다 A 와 B 를 번갈아 호출했다.

### 5-3. 표본 대조: 제목·요약문만으로 쓴 문장은 본문과 어긋나는가

서비스는 기사 본문이 아니라 제목과 잘린 요약문(3-2)만 모델에 넣는다. 그래서 "앞 100여 자만 보고 쓴 문장이 본문과 어긋나지 않는가"를 한 번 표본으로 확인했다. 원문: `docs/experiments/2026-11-18-input-vs-fulltext-sample.md`.

**방법.** 대상은 운영 서버의 2026-11-18 21:03 실행(id 4, 예비 모델 `gemini-3.5-flash-lite`, 이슈 문장 22개)과 21:38 실행(id 5, 주 모델 `claude-haiku-5-5`, 이슈 문장 28개)이다. 두 실행 모두 저장된 기사는 47건이고 링크 기준 46건이며, 그 46건 중 43건이 같은 기사다. 기사 원문 링크를 열어 요약문이 본문의 어느 부분인지 보고, 문장을 두 가지로 판정했다. "입력 대비"는 인용 기사의 제목+요약문만으로 문장이 뒷받침되는가이고, "본문 대비"는 본문과 어긋나지 않는가(본문을 연 경우만)다. 1차 판정은 AI 평가자(Claude Sonnet) 한 명이 했고, 일치가 아닌 항목은 작업 세션이 입력 원자료와 원문으로 다시 확인했다.

- 주 모델 "일부만" 3개: SK하이닉스("올해 본예산 6조원"으로 연도를 입력에 없는 쪽으로 붙임), 삼성전자우("미래에셋증권에서 거래하는 고수익 투자자들"이라는 한정을 뺌), 하이브(잘린 문장 "올해 3분기 새로 쓴 기록이다"가 가리키는 것을 문장이 누적 매출로 이음). 주 모델 "맥락 누락" 4개: 영업이익 감소의 비교 기준(전분기 대비), MLCC 협력 단계(경계 사례), 두산에너빌리티 지원 규모, 키홀더 인수가 지분 취득 예정이라는 점. 뒤의 세 개는 예비 모델에서도 같은 기사에서 나온 누락이다.

**말할 수 있는 것.**
- 이번 표본에서 예비 모델 문장 22개 중 20개, 주 모델 문장 28개 중 25개는 인용한 기사의 제목·요약문으로 뒷받침됐다. 나머지는 주체가 바뀌었거나, 잘린 요약문에서 추론했거나, 한정 조건이 빠진 것이다.
- 본문을 확인할 수 있었던 문장(예비 13개, 주 20개) 중 본문과 어긋난 문장은 찾지 못했고, 예비 3개·주 4개는 중요한 조건이 빠져 있었다.
- 읽을 수 있었던 기사 31건 중 26건은 제목+요약문만으로 핵심 사실을 알 수 있었다.
- 표본 대조 중 종목 귀속 오류(에스엠 종목의 에스엠벡셀 기사)를 찾았고 필터를 고쳤다(3-2). 이 오류는 문장이 인용 기사와 일치해서 위 판정으로는 잡히지 않는다.

**말할 수 없는 것.**
- "본문과 어긋나는 문장이 없다." 예비 모델 표본에서 9개는 본문을 열지 못해 판정하지 못했다. 네이버 뉴스 링크 9건은 통째로 빠졌다.
- "기사를 요약한다", "원문과 대조해 검증한다." 서비스는 본문을 읽지 않는다. 이 대조는 일회성 표본 확인이다.
- "Haiku 가 예비 모델보다 본문에 충실하다." 두 모델의 비율이 약 90%로 비슷하다(20/22, 25/28). 문장 수가 적어 어느 모델이 더 낫다고 말할 수 없다.
- "Haiku 는 확인 안 된 숫자가 없다." 같은 모델·같은 프롬프트인데 id 5 는 0개, id 6 은 2개다.

**id 6 의 확인 안 된 숫자 2개(결정 기록 6번).** NAVER "0.47%": 인용 기사 요약문이 "800원(0.47..." 에서 잘려 있고 모델이 "%" 를 붙여 문장을 완성했다. 값은 요약문의 숫자와 같다(800원 ÷ 17만원 ≈ 0.47%, 계산값). 삼성SDI "18일": 인용 기사의 제목·요약문에 날짜가 없고 프롬프트에는 기사 발행일이 들어가지 않으므로 같은 종목의 다른 기사에서 가져온 것으로 보인다(추정).

**한계.** 같은 날 두 시점, 문장 22개와 28개. 1차 평가자는 AI 한 명이고 사람이 전수 확인하지 않았다. 원문은 웹 페이지를 요약해 주는 도구를 거쳐 읽었다. 본문 전체를 직접 읽은 것이 아니어서 수치 일부에 오류가 있을 수 있다. 평가자와 재확인 모두 Anthropic 모델이고 주 모델 표본은 같은 회사 모델의 출력이다. 같은 회사끼리의 평가가 판정을 후하게 만들었는지는 확인하지 않았다.

### 7-1. 항목별 상세

**(a) 20:00 정기 실행 실패와 원인 미확인.**
- 사실(`GET /api/runs`, id 3): 2026-11-18 20:00:00 정기 실행에서 10종목 모두 `AI_CALL_FAILED`, 분석 시도 107.6초, 전체 124.0초. 이 실행의 분석 모델 칸은 비어 있다. 직전 두 번(18:51, 19:00)은 10/10 성공이었다. 대체 문구는 저장되지 않았고 화면에는 실패로 표시됐다. 개선 전이었다면 미리 써둔 문구가 "AI 분석"으로 저장됐을 상황이다.
- 당시 배포본이 시도한 모델 목록은 `gemini-2.5-flash, gemini-3.8-flash, gemini-1.5-flash`(커밋 `80ec9924` 이전 코드의 기본값)였다.
- **원인은 확인하지 못했다.** 한도 초과인지 과부하인지, 뒤의 두 모델이 호출 가능한 모델이었는지 알 수 없다. 당시 컨테이너 로그는 이후 재배포로 컨테이너가 교체되면서 확인할 수 없게 됐다고 전해 들었다(로그를 직접 확인하지는 못함). 따라서 "Gemini 한 회사에 몰려서 실패했다"는 추정일 뿐이다.
- 이 사건은 두 회사 체인으로 바꾼 동기의 하나이지만, 체인이 이 실패를 막는다는 것을 시험한 것은 아니다(결정 기록 7번). 이후 실행 3회(id 4~6)가 성공했을 뿐이다.
- 이 일에서 얻은 개선점: 실행 이력이 있어서 실패가 기록으로 남았다. 실패 원인 로그가 재배포로 사라지는 문제는 남아 있다(8장).

**(b) 첫 배포 뒤 주 모델이 아니라 예비 모델이 응답한 일.**
- 사실: 모델 체인을 배포한 뒤 첫 실행(2026-11-18 21:02, id 4)에서 응답한 모델이 `claude-haiku-5-5` 가 아니라 `gemini-3.5-flash-lite` 였다. 서버 환경 파일에 Anthropic 키가 없었다. 체인은 키가 없는 제공자를 건너뛰므로 예비 모델이 응답했고, 화면에는 실제로 응답한 모델 이름이 표시된다.
- 조치: 서버에 키를 넣고 재시작했다. 다음 실행(21:38, id 5)부터 `claude-haiku-5-5` 가 응답했다.
- 의미와 한계: "키 없는 제공자는 건너뛴다"는 동작을 운영에서 본 사례다. 주 모델이 호출됐다가 실패해 예비로 넘어간 경우는 운영에서 보지 못했다. 키 누락이 코드가 아니라 서버 설정의 문제였다는 점, 배포 후 응답 모델을 이력으로 확인해 알아냈다는 점이 이 일의 요점이다. 키 값은 이 문서에 쓰지 않는다.

**(c) 에스엠/에스엠벡셀 종목 귀속 오류의 발견과 수정.**
- 발견: 제목·요약문 대 본문 표본 대조(5-3) 중 종목 "에스엠"(엔터테인먼트)의 기사 5건 중 3건이 "에스엠벡셀"(배터리 제조) 기사임을 알았다. 이슈 문장도 에스엠 종목 아래에 에스엠벡셀의 군용 배터리 공급계약을 썼다. 근거 번호는 실제 기사를 가리켰기 때문에 근거 유효율 같은 기존 지표로는 잡히지 않았다.
- 원인: 필터가 "제목에 종목명이 들어 있는가"만 봤다.
- 수정: 종목명 뒤에 한글·영문·숫자가 이어지면 제외하는 규칙(3-2, 커밋 `d2f399fd`). 효과·부작용·운영에서 확인한 범위와 확인하지 못한 범위는 3-2 에 있다.
- 과거에도 있었던 유형인가: 같은 규칙을 과거 아카이브 1,487건에 적용하면 29건(1.9%)이 제외된다(3-2). 이 29건은 따로 상장된 회사 13건, 자회사·브랜드 14건, ETF 상품명 2건이라 모두 오귀속이라고 말할 수는 없지만, 같은 유형의 문제가 보관분에도 있었다는 근거는 된다.

**(d) 확인 안 된 숫자 4개가 전부 표기 차이였던 일.**
- 사실: id 4 의 숫자 총수 48 중 확인 안 된 4개는 모두 값은 맞고 표기만 달랐다(기사 "436,000원" → 문장 "43만6000원", 기사 "158,000원" → 문장 "15만8000원" 등. 결정 기록 6번). 검사는 숫자 문자열이 인용 기사에 있는지만 보므로 표기가 다르면 불일치로 잡는다.
- 의미: 이 지표를 "환각 건수"라고 말하면 틀리다. 그래서 운영에서는 문장을 자동으로 고치거나 지우지 않고 측정만 한다.
- 반대 방향의 한계: 맥락이 달라도 같은 숫자면 일치로 잡힌다. id 6 의 2개는 표기 차이가 아니라 잘린 요약문을 모델이 완성한 것(NAVER "0.47%")과 인용 기사에 없는 날짜(삼성SDI "18일", 같은 종목의 다른 기사에서 가져온 것으로 추정)였다(5-3).

## 8. 남은 과제와 한계
- **기사 본문**: 2026-11-18 까지의 운영 상태에서 서비스는 기사 본문을 읽지 않았고 제목과 잘린 요약문(109~139자)만 모델에 넣었다. 본문을 수집하지 않은 이유는 판단(미측정)이다: 언론사 32개 도메인에 흩어져 있어 구조가 사이트마다 달라 종목 수집과 같은 변경 위험이 있고, 본문 수집·저장의 저작권·이용약관 검토를 하지 않았다(결정 기록 2번).
  - 2026-11-19 에 본문 수집을 구현해 배포했다(3-2). 서버 측정은 한 번(id 7)뿐이다. 본문 입력 후의 문장을 본문과 대조하지 않았으므로 "본문을 넣어 환각이 줄었다"고 말할 수 없다. 추출 실패 4건(원문 언론사 페이지가 지정한 선택자에 걸리지 않음)은 요약문으로 분석된다. 언론사별 이용약관과 법적 허용 범위는 확인하지 않았다. 본문 수집 후의 서버 메모리는 재지 않았다.
- 수집 주소가 공식 Open API 가 아니다. 공식 전환 후보(공공데이터포털 주식시세정보 등)는 조사만 했고 비교 기록은 없다.
- 뉴스 관련성: 종목 귀속 필터(3-2)로 "종목명이 다른 단어의 일부로만 나온 기사"는 걸러진다. 종목명과 이름이 같은 다른 회사, 제목에는 종목명이 있으나 주인공이 다른 종목인 기사, 모회사 이름이 없는 자회사 기사(제외됨)는 남은 한계다. 필터가 운영에서 실제로 제외한 건수는 확인하지 못했다.
- 문장 충실도 평가는 일회성 표본(문장 22개·28개, AI 평가자 1명, 본문을 열지 못한 기사 14건)이다. 상시 측정은 하지 않는다. 사람이 전수 확인한 값이 아니다.
- 모델 선택: 모델당 3회, 한 시점의 입력, 통계 검증 없음. 다른 날의 입력과 반복 수 확대가 남아 있다. `gpt-6-luna` 대신 Haiku 를 고른 실제 이유는 발표자가 확정해야 한다(4-3).
- 체인의 두 번째 모델로 실제 장애를 넘긴 운영 기록이 없다. 20:00 실패(id 3)의 원인은 미확인이고 그 시점 로그를 보존하지 못했다. 로그를 오래 보존하거나 실패 알림을 보내는 방법이 필요하다(알림은 아직 없음, 결정 기록 10번).
- 한 번의 호출에 10종목을 넣어서 한 번 실패하면 10종목이 함께 실패한다. 종목별 호출과 비교한 적이 없다(결정 기록 3번).
- 수치 근거 측정은 문자열 일치라서 표기 차이를 불일치로 잡고(7장 (d)) 맥락이 달라도 같은 숫자면 일치로 잡는다.
- Spring Boot 4.x 전환.
- Vercel → 백엔드 구간이 평문 HTTP 다. 백엔드 HTTPS 적용 필요.
- 실행 이력 표본이 6회뿐이고 모델이 섞여 있다. 오래된 이력 정리 로직도 없다.
- 네이버 검색 API 가 다른 플랫폼으로 이관 중이다. 사용 중인 키의 발급처와 약관(AI 활용 제한 여부) 확인 필요.
- 작업 중 대화에 노출된 DB 비밀번호·API 키는 교체해야 한다.
- 운영 서버의 부하 중 최대 메모리 사용량은 측정하지 않았다(측정한 것은 대기 상태 두 번: 266.6MiB, 그리고 Anthropic SDK 포함 JAR 에서 304.2MiB / 512MiB). 본문 수집을 넣은 뒤의 값은 배포 후 다시 재야 한다(결정 기록 14번).

## 9. 다시 확인하는 방법
```bash
# 백엔드 테스트 (216개: 실패 0, 오류 0, 건너뜀 3 이 마지막으로 확인된 값)
cd backend && ./gradlew test --console=plain

# 운영 상태와 실행 이력 (읽기 전용 GET)
curl http://211.188.54.232:8080/api/health
curl "http://211.188.54.232:8080/api/runs/summary?hours=24"
curl "http://211.188.54.232:8080/api/runs?limit=20"

# 표본 대조에 쓴 것과 같은 형식의 자료 (종목, 종목별 기사)
curl http://211.188.54.232:8080/api/stocks/top10
curl http://211.188.54.232:8080/api/stocks/{id}/news

# 모델 비교 실험 (키는 환경변수로, 예: ANTHROPIC_API_KEY. 없는 제공자는 건너뜀)
cd backend && ./gradlew modelExperiment
# 결과: backend/build/experiment/summary.md, result.json
```
- 위 명령은 현재 코드와 맞는지 확인했다: 컨트롤러에 `GET /api/runs`(`limit` 기본 50, 1~200), `GET /api/runs/summary`(`hours` 기본 24, 1~720), `GET /api/health`, `GET /api/stocks/top10`, `GET /api/stocks/{id}/news` 가 있고, `build.gradle` 에 `modelExperiment` 작업이 있다(이번에 파일을 읽어 확인. gradle 은 실행하지 않았다). `./gradlew test --console=plain` 은 CLAUDE.md 의 명령과 같다.
- 모델 체인 설정: 환경변수 `ANALYSIS_MODELS`(비어 있으면 기본 `claude:claude-haiku-5-5,gemini:gemini-3.5-flash-lite`), 서버 환경 파일의 `ANTHROPIC_API_KEY`(`docker-compose.server.yml`).
- 표본 대조의 판정 원자료(기사 제목·요약문·링크)는 저장소에 넣지 않았다. 위 두 GET 으로 같은 형식을 다시 받을 수 있고, 수집분은 시간이 지나면 바뀐다.

## 10. 발표에서 조심할 표현
- "gpt-6-luna 가 OpenAI 최저가"는 틀리다. 이전 세대 `gpt-5-nano` 가 더 싸다. "최신 세대 중 최저가"로 한정한다.
- 실험은 차수마다 모델당 3회이고, 세 차수 모두 같은 날 저녁의 비슷한 입력이다. "가장 우수하다"가 아니라 "이 조건에서 이렇게 측정됐다"로 말한다.
- Gemma 의 결과는 "Gemini API 의 무료 등급으로 호출했을 때"의 것이다. 자체 서버에 설치했을 때의 성능이 아니다.
- 국산 모델의 "국내 데이터 처리"는 HyperCLOVA X 의 지원 리전이 "한국"이라는 것까지만 확인했다.
- 가격과 종료 일정은 2026-11-18 에 공식 페이지를 요약 도구로 읽은 값이다. 발표 직전에 원문을 열어 대조한다.
- 이 프로젝트는 AI 도구(Claude Code)를 써서 만들었다. 본인이 한 일(문제 정의, 판단, 서버 구성, 키 관리, 검증 확인)과 도구가 한 일을 구분해 말한다.
- **쓰면 안 되는 표현**(이유는 근거 문서에 있다):
  - "기사를 요약한다" — 서비스는 제목과 잘린 요약문 100여 자만 본다(3-2, 결정 기록 2번). "제목과 요약문 기반 이슈 정리"로 말한다.
  - "원문과 대조해 검증한다" — 서비스는 본문을 읽지 않는다. 본문 대조는 한 번 한 표본 확인이고(5-3), 서비스 기능이 아니다. 서비스가 매번 하는 검증은 근거 번호의 유효성 확인과 숫자 문자열 대조(측정만)다.
  - "본문과 어긋나는 문장이 없다" — 판정하지 못한 문장이 있다(예비 모델 표본 9개).
  - "Haiku 가 더 충실하다" — 두 모델의 비율은 약 90%로 비슷했고 표본이 작다(20/22, 25/28).
  - "Haiku 는 확인 안 된 숫자가 없다" — id 5 는 0개, id 6 은 2개다.
  - "확인 안 된 숫자 = 환각" — 4개 모두 표기 차이였던 사례가 있다(7장 (d)).
  - "Haiku 가 GPT 보다 우수하다고 측정됐다" — 숫자 포함 비율은 비슷했고 비용은 `gpt-6-luna` 가 낮았다(4-3). "비슷했다"가 측정과 맞는다.
  - "두 회사 체인이라 장애에 안정적이다" — 체인으로 실제 장애를 넘긴 운영 기록이 없고, 20:00 실패(id 3)의 원인은 미확인이다.
  - "필터가 다른 회사 기사를 모두 걸러낸다" — 운영 로그로 확인한 것은 id 6 실행 한 번에서 5건(에스엠벡셀 4, 하이브재팬 1)이 제외됐다는 것이다. 종목명과 이름이 같은 다른 회사 등은 여전히 걸러내지 못한다(3-2).
  - 근거 없는 수식어("안정적", "대폭 개선")는 쓰지 않는다. 숫자와 조건으로 말한다.
- 20:00 실패(id 3)를 숨기지 않는다. 숨기지 않는 쪽이 "실패를 상태값으로 드러낸다"는 이 프로젝트의 원칙과 맞다. 다만 원인은 모른다고 말한다.
- 월 비용(`gpt-6-luna` 약 $0.8 대 Haiku 약 $1.5)은 1회 비용에 13회 × 약 21거래일을 곱한 계산값·추정이다. 실제 청구액이 아니다.
- 기사 본문 수집 기능에 대해서는 측정 전이므로 단정하지 않는다. "서비스는 기사 본문을 읽지 않는다"는 2026-11-18 까지의 운영 상태에 대한 문장이다.
